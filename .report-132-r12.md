## What this round delivers, and why it is the bounded change

Issue #132's own text names the shape that must hold: *"the run's `merge` step
must never leave the integration checkout diverged from the published
integration ref, and the run must be able to complete on a repo whose policy
is squash."*

The merge-side half is in the base (#156/#168/#178/#182; #196 lands and
publishes under the plan's `merge_policy`, with the published ref always the
certified target, never a stale local view). The still-unlanded half is the
`cleanup` side: **when the sanctioned landing happens on the forge (the PR is
squash-merged), the checkout's own integration ref never sees it, so `cleanup`
must prove the landing against the FETCHED, verified PUBLISHED ref — and only
a checkout strictly behind it may certify from that view.** That content is
independently PASSed in the review lineage (`REVIEW-183-024783d4`,
`REVIEW-183-f4ea6876` — the latter names
`f4ea6876cb0ac8d39729f1a4bbfabe4eb2250a2b` exactly) and is replayed here onto
the rebuilt run base — the lineage's own refresh shape, never a re-design:

- `LandedProof::Published { published_head, merge_base }` — the third landed
  proof (ancestry / local content / published content), made against the
  fetched published head.
- `landed_in_published` — reads the published head
  (`published_integration_head`), refuses when the checkout's own ref IS the
  published view (no self-certification), FETCHES and verifies it
  (`fetched_published_head`), refuses whenever the local ref is not a strict
  ancestor of it (an unpublished or diverged local move is never certified),
  then proves the branch head by ancestry against the fetched head, or — for
  the squash landing, which never is an ancestor — by exact content on every
  path the branch changed relative to the fork point.
- `effect_cleanup` — when the local proof refuses `refusal.cleanup.unmerged`,
  tries the published route; if that view adds no proof, the ORIGINAL local
  refusal is returned unchanged. The salvage record of a published proof names
  `published_head` (and `merge_base` when the proof was by content) while
  keeping the checkout's own `integration_head`; deletion uses `-D`.
- `landed_in_integration` uses the base's shared fail-closed comparison
  helpers (`changed_paths_between`, `differing_paths_between`, landed with
  #196) instead of the round-5 private helper, so the local and the published
  proofs cannot drift.

Staging has moved two commits since the reviewed head's base

replay is added in this round. The round-10 and round-11 report files are

## Residual tension (recorded, not resolved here)

Cleanup's published route certifies a landing the forge performed; it never
performs or claims a forge merge itself (`spec-lifecycle.md`, `spec-plans.md`
state this explicitly). A run whose `merge` step must land by push on a
PR-protected integration ref still cannot complete end-to-end without either
(a) the forge landing performed externally and then certified here, or (b) the
owner ruling that changes the landing form. Recorded so round 12 is not read
as closing that question.
