## 1. The mechanism (traced from the failing runner to the retry row)

The run's own supervision re-dispatches a diagnosed step through the daemon's
apply path (`DaemonDispatch::dispatch_at` -> `method_apply` ->
`mutation::execute_step`). For the live p6 shape the step kind is
`review_evidence`, so the effect materializes the reviewer leg's OWN lane
checkout first:

- `ensure_reviewer_lane` (src/mutation.rs) resolves the leg's lane from
  `crate::lane::lane_checkout(issue, "reviewer", round)` — `issues-<N>-rev<R>` —
  refuses a plan that binds any other leg's checkout, and, the directory being
  absent, runs `git worktree add --detach <lane> <certified head>`.
- The acceptance integration clone still held a REGISTRATION for that exact
  path while the directory was gone, so git refused the create (exit 128):
  `fatal: '<worktrees root>/issues-<N>-rev2' is a missing but already
  registered worktree; use 'add -f' to override, or 'prune' or 'remove' to
  clear`. The engine is right to fail closed — the host state is what is stale.
- That failure is a bare `adapter.exit`, so supervision spent the step's
  bounded retry (`State::consume_supervised_retry`, `rt_*` rows), and after
  three of them the daemon refused further dispatches with
  `refusal.run.retry_bound`: the run could not re-dispatch, could not
  terminate, and kept counting against the per-repository cap.

## 2. The remedy chosen, and why

**Remedy 1 — heal it** (the issue's first option). A registration git still
holds for the exact path this step is about to create, while that path's
directory is gone, is stale host state with a mechanical remedy: the engine
clears it for that ONE path before the create, through git's own
`worktree remove`, and records the repair on the step outcome
(`stale_registration`).

Why this one, and not an exemption or an escapable park:

- it removes the failure instead of re-pricing it: with the registration gone
  the dispatch SUCCEEDS, so no bounded retry is ever charged for this class
  (strictly stronger than "does not consume a retry"), and the run advances
  under its own supervision with zero operator keys;
- the engine already owns exactly this repair policy at exactly this scope for
  the sibling stale-state classes (#190/#222 reclaim a terminal generation's
  residue): the same read, the same host, the same "only the registered path
  THIS step is about to create" scoping, so an operator retire and a
  bind-time repair can never diverge;
- AC4 therefore holds by construction — no arm was added to the retry
  accounting, so a genuine step failure still consumes a bounded retry exactly
  as today and `retry_bound` still escalates when the budget is spent on real
  failures. The control witness below pins that.

Remedy 2 ("don't charge it") was NOT implemented: it would price-stamp a
failure the engine can repair, and it needs a new classification arm in the
supervision/retry accounting (the widest surface in the repository) — the
over-broad exemption AC4 warns against.

Remedy 3 ("escapable park") was NOT implemented: making a run terminal by
itself at `retry_bound` changes what a run may do to itself, which issue #146
deliberately reserves for the explicit, audited `run.release` control.

The issue allows "either or both"; one remedy is chosen and justified here, and
its residual limits are listed in section 5.

Scoping, stated because the issue asks which policy is implemented: only a
path that is ABSENT **and** registered by the integration clone is addressed; a
present checkout is never touched (the duplicate-lane refusals stay the
answer); a path this clone does not register is left alone; another leg's lane
is a different path; no branch is ever deleted; a locked registration is left
to git, whose refusal stays the step's own failure.

Sites healed (one shared helper, `clear_stale_lane_registration`):

1. `effect_worktree_create` — the run's own implementer lane (branch + checkout);
2. `ensure_reviewer_lane` — the reviewer leg's lane (the measured live shape);
3. `ensure_fix_lane` — the fix leg's lane created by a recorded review FAIL.

The path comparison tolerates a deleted leaf: `resolved_lane_path` canonicalizes
the deepest EXISTING ancestor and re-appends the missing tail, so git's
resolved report (a symlinked temp root, e.g. `/var` -> `/private/var`) still
matches the path the engine is about to create; the literal path form is
accepted too.

## 5. What I could NOT verify

- **The two live runs' unparking is NOT proven, and this change does not
  unpark them.** Their bounded retry budget was already spent before this fix
  (`refusal.run.retry_bound`), and the issue fences them: no operator `run.*`
  control, no `state.db` write, no lane or retry-row touch — I made only
  read-only reads. They stay wedged until an operator uses the documented
  `run.release` control. What is proven is on fixtures: a run that meets the
  same host state never dies on it, so its budget is never spent by this class
  in the first place. Remedy 3 (escapable park) was deliberately not
  implemented (section 2).
- **AC3's literal `queue preview` read is not driven end-to-end.** The read
  that frees a counted slot is the run's own completion inside `queue_advance`
  (a verified delivery on the run's last committed spine step); no fixture in
  this lane drives a full delivery. Witnessed instead (W1): this class can no
  longer pin a slot, because the run advances under its own supervision
  (frontier `p3`, next step landed, zero retries minted, no `retry_bound`
  record). The issue's own quoted preview read
  (`refusal.admission.cap_repository`, both wedged runs named as active lanes)
  is pre-existing evidence from the issue, not re-run here.
- **A repair that itself fails.** If git refuses `worktree remove` (for example
  a LOCKED stale registration), the failure is propagated as the step's own
  error and that attempt is still charged a bounded retry exactly as today; no
  new typed code was added for that residual, and no fixture covers a locked
  registration.
- **The fix leg's repair is not separately recorded** on the fix-round receipt
  (`stale_registration` rides the `worktree_create` and `review_evidence`
  outcomes; the fix round's document has its own closed schema). W3 witnesses
  the effect, not a receipt field.
- Only these three lane-materialization sites were changed; no other `git`
  create path in the repository was audited for the same stale-registration
  shape.
- The raw logs cited above live under `/tmp` and are not part of the
  repository; this report file is the lane's tracked deliverable.
