### Conflict 1 — `src/supervision.rs` (the dispatch park list)

- New base: `if crate::state::step_attempt_diagnosed(status, code)`, with the
  per-code park list moved one level down into the driver's own-retry arm —
  `(!authorized && code != WORKER_TIMEOUT && code != VERDICT_STALE && … &&
  step_retries.len() < RUN_RETRY_MAX)`, which is the issue #241 change.
- Branch: `&& code != crate::mutation::code::LANE_TIMEOUT` beside the
  `WORKER_TIMEOUT` exclusion.

What `step_attempt_diagnosed` actually subsumes (`src/state.rs:251`): it is
`status ∈ {failed, refused, ambiguous}` minus the run's-own-lapsed-window codes
(`GRANT_EXPIRED`, `PROOF_STALE`, `PROOF_MISSING`; issues #184/#250). It
subsumes **no** park code — the park codes moved down into the `!authorized`
arm at the new base, which is exactly where #224's exclusion belongs: #224's
own comment calls the lane timeout "the same wait/park" as the worker timeout.

Resolution: staging's guard verbatim (`src/supervision.rs:861`), plus
`&& code != crate::mutation::code::LANE_TIMEOUT` added beside the
`WORKER_TIMEOUT` exclusion, carrying #224's comment at the new seat
(`src/supervision.rs:891-898`). The helper was **not** modified.

Why #224's semantics survive: a `cleanup` frontier is a committed TAIL kind
(`COMMITTED_TAIL_STEP_KINDS = ["merge", "cleanup"]`, `src/supervision.rs:200`),
so `authorized && !tail` is false for it and the decision is taken by the
`!authorized` arm — where the lane timeout is now excluded exactly like the
worker timeout. The parked frontier returns `None` from `dispatch_intent`
(never re-dispatched, no bounded retry minted) and still classifies
`needs-attention` with the recorded `effect.lane_timeout` as the detail.

The one path the new base lets past the park codes is an operator-held
authorization over a NON-tail step; a `lane_timeout` can only be recorded by
the `cleanup` effect, a tail kind, so both placements park that frontier
identically — the exclusion is at the same strength as the new base's own
`WORKER_TIMEOUT` exclusion and no weaker. The shipped dispatch-layer pin
`supervision::tests::a_lane_wait_timeout_parks_the_cleanup_frontier_without_burning_a_bounded_retry`
(`src/supervision.rs:3336`, part of #224) is green at the new head and bites
this guard: without the `LANE_TIMEOUT` exclusion that fixture is dispatchable
and the test's `dispatch_intent(...).is_none()` assertion fails.
