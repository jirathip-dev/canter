## The four recorded failures and what changed

1. `ci_suite_matrix_registration_for_new_test` — `tests/queue_intake.rs`
   landed without joining the `rust-ubuntu-suite` matrix. The repository's own
   guard (`scripts/test-ci-test-driver.py`,
   `InvocationTests.test_matrix_enumerates_every_suite_once`, "matrix must
   match every `tests/*.rs` plus lib/bins/doc") is what failed in the hosted
   `rust-ubuntu-build` leg; the mutation below reproduces its message
   verbatim. Fixed by adding `--test queue_intake` to the matrix once, in
   ascending suite order (`.github/workflows/ci.yml`).

2. `hosted_ci_head_census` — the only red legs at the certified head were
   `rust-ubuntu-build` (the guard above) and `rust-ubuntu` (`build=failure
   suites=skipped`); both trace to the same unregistered suite, and with the
   matrix fixed the pushed head carries no lane-caused failure (hosted
   read-back below).

3. `hosted_ci_red_base_symmetry_adjudication` — the base is NOT clean: run
   `35745675850` at `277fdd9456` records `rust-macos` FAIL with
   `tests/review_dispatch.rs::a_re_attempted_review_step_consumes_the_late_verdict_without_re_prompting_the_leg`
   panicking at `tests/review_dispatch.rs:1497` (`left:
   Some("adapter.timeout") / right: Some("effect.review_timeout")`) — the
   repository's documented load-flake class (named in `.report-225.md` and
   prior rounds). The other 50 check runs at the base are green, and the
   head's OWN `rust-macos` leg PASSED at `e7bf162`. So: the base red is a
   pre-existing intermittent; the head red is entirely the lane's own
   (matrix) failure, fixed in (1); nothing remains to attribute.

4. `ac1_commit_leg_end_to_end_witness` — the commit leg (`--out`, no
   `--dry-run`) was wired but unwitnessed; the reviewed lane report disclosed
   exactly that gap. `tests/queue_intake.rs` now carries
   `the_commit_leg_commits_one_run_per_admitted_item_over_a_live_daemon`: one
   invocation over a REAL daemon child renders the bound-input document to
   `--out`, mints one grant per selected item and commits ONE admitted run
   per admitted item, all through the same surfaces the operator path uses
   (the intake command itself drives `queue preview` → `grant issue` →
   `queue submit`). The witness asserts the committed submission document
   (`hf-queue-submission/v1`, admission 2 admitted / 0 waiting / 0 refused),
   that each admitted item names its OWN run id, that the written document is
   the operator path's `hf-queue-preview/v1` bound-input document, and —
   after the daemon shuts down — that the store holds exactly two run rows
   whose ids match the ones the submission named, plus one ownership row per
   admitted item. The daemon child is held in a `Daemon` guard that kills and
   reaps it on drop, so a failing assertion can never leak a fixture daemon
   into the driver's survivor sweep.
