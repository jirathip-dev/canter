## 2. What changed (bounded)

- `src/service.rs`:
  - `UnitEnvironment` + `unit_environment()` — the unit's `PATH`/`HOME` are
    derived from the INVOKING environment (the environment the operator ran
    `install-plan` in); `None` when the invoking environment carries none.
    Never a hardcoded host path list.
  - `checked_unit_environment()` — every configured harness executable is
    resolved with the daemon's own rule (`adapters::resolve_executable` over
    the declared `PATH`); the first that does not resolve refuses typed:
    `refusal.service.harness_unresolved`, naming the harness, its
    executable, and the checked PATH.
  - `launchd_unit()` renders `<key>EnvironmentVariables</key>` (PATH, HOME),
    `StandardOutPath`/`StandardErrorPath`; `systemd_unit()` renders
    `Environment="PATH=…"` / `Environment="HOME=…"` and
    `StandardOutput=append:`/`StandardError=append:`. Values are XML-escaped
    (plist) / quote-escaped (systemd) so any real PATH or home stays one
    well-formed value.
  - `install_plan_steps()` prepares the state dir (0700) the log capture
    needs to exist, and names the captured log paths in its own step — so a
    failed start is diagnosable from the plan output alone (AC3).
- `src/commands.rs` (`service install-plan|status-plan|uninstall-plan`):
  `--json` data now carries `environment` (the declared PATH/HOME) and
  `logs` (stdout/stderr paths); the human plan prints both; and the
  environment derivation gates the INSTALL only — `install-plan` refuses
  (exit 4, typed) while `status-plan`/`uninstall-plan` keep rendering so a
  bad install stays inspectable and removable.
- `docs/OPERATIONS.md` §5.1: the rule, the refusal, the log capture, and why
  `GIT_TEMPLATE_DIR` is deliberately NOT rendered (below). Help text for
  `service` states the same contract.
- Tests: three integration witnesses in `tests/service_plans.rs` (render,
  refusal + gating scope, positive control) and six unit tests in
  `src/service.rs` (derivation, refusal, both renderers, steps), on top of
  the existing suite.

### Design notes (deliberate choices)

- **PATH = the invoking PATH, verbatim.** The daemon inherits its
  environment from the service manager; every subprocess it spawns resolves
  its executable through that environment. The operator's PATH is the one
  environment known to resolve the operator's tools, so the unit declares
  it; the derivation adds nothing and invents nothing. The refusal is the
  guard that keeps a unit from being rendered for an environment that cannot
  reach a configured harness.
- **`GIT_TEMPLATE_DIR` is NOT rendered** (issue item 2's "or state why
  not"): the scratch-`git init` class (issue #226) requires `git
  init`/`git clone`, and the daemon's own git surface runs neither (code
  census: rev-parse, worktree add/remove, merge-base, status, fetch,
  ls-remote, cat-file, push/rebase/merge). `git worktree add` — the
  daemon's only repository-creating operation — does not copy the host
  template directory: a probe planted a template hook in `GIT_TEMPLATE_DIR`
  and a worktree created through it contains no copy of it. Operators who
  want defense-in-depth can still add the variable by hand; the ops doc
  says so.
- **A distinct typed code.** The refusal is
  `refusal.service.harness_unresolved`, not the runtime
  `refusal.unavailable.harness`: install-time gating (this unit could never
  reach the executable) and run-time spawn failure (a child could not be
  spawned) are different facts at different surfaces, and an operator
  reading the code must be able to tell them apart. The install gate is what
  prevents the second from happening on this class.
- **The state-dir step is additive.** The daemon creates its own dirs
  (0700) on start, but the service manager opens the log files BEFORE the
  daemon runs, so the rendered steps create the dir first. Disclosed as the
  one added operation in the install plan beyond the issue's three items.
- Disclosed small fix inside the same change: plist string values are now
  XML-escaped (the environment values make arbitrary operator PATHs a real
  possibility inside `<string>`; previously only fixed paths were
  interpolated). No behavior change for paths without `&`/`<`/`>`.

### 3b. Hosted CI findings (why `069a459` exists)

The first pushed head (`5206b96`) ran hosted CI (run `36169478895` for the
PR) and reported three failing jobs. Each was adjudicated separately:

1. **`rust-ubuntu (--test service_plans)` — a REAL defect in the lane's own
   test, fixed in `069a459`.** On Linux the plan renders the systemd branch,
   whose `Environment="PATH=…"` line contains quotes; inside the JSON
   envelope those are escaped, so the test's raw-substring assertion
   (`tests/service_plans.rs:301`) could never hold there — the PRODUCT
   output was correct, the assertion was wrong (`hosted-service_plans-log.txt`,
   raw envelope quoted in the panic). Fix: parse the envelope
   (`serde_json`, an existing dev-dependency) and assert against the parsed
   `data.unit` text and the parsed `environment`/`logs`/`steps` values.
   Verified locally by a forced-systemd probe: `detect_platform()` and the
   test's platform branch flipped to the systemd path, the fixed witness runs
   GREEN (exit 0, `systemd-probe-green.log`), and both flipped files were
   restored (`src/service.rs` byte-equal to the committed blob; the test
   branch condition restored). The focused suites were re-run green at the
   fixed content (W1/W2). The same flip against the OLD assertion is the
   hosted failure itself (panic above).
2. **`rust-ubuntu (--test queue_advance)` — hosted-runner flake,
   pre-existing at the base.** The failing test
   (`a_fix_rounds_delivered_head_is_re_bound_by_the_runs_own_machinery`,
