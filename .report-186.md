## Root cause: "the file exists" is not "the record is readable"

Pre-fix reader (`witness()`, used by both real-driver tests):

```python
while not pid_file.exists() and child.poll() is None:
    ...
record = json.loads(pid_file.read_text())
```

Pre-fix writer (the escape fixture the test writes into its temp dir):

```python
Path(sys.argv[1]).write_text(json.dumps({...}))
```

`Path.write_text` opens with mode `w` — creating/truncating the file, immediately visible to
`exists()` — and the payload reaches the page cache only when the buffered stream closes. For the
whole open→close interval the file EXISTS and is zero-length, while the reader treats existence as
readiness and parses it: exactly the CI error string above.

Measured publication window (20000 `write_text` publications per host; the interval an
existence-checking reader can land in):

| Host | p50 | p90 | p99 | max |
| --- | ---: | ---: | ---: | ---: |
| Linux node (load ~4, Python 3.14) | 12.0 µs | 15.5 µs | 18.9 µs | 528.5 µs |
| macOS lane host (shared, load ~70) | 114.5 µs | 139.2 µs | 311.8 µs | 5582.0 µs |

Deterministic mechanism proof (same code paths, same host): a writer that holds the file open the
way `write_text` does (open → content → close) with the pre-fix reader body watching it reproduces
the CI failure exactly — `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`,
raw exit 1 — while a contract-style reader on the same publication succeeds, raw exit 0. A
tight-loop stat over 2000 real `write_text` publications saw the file existing-but-empty in 9518
of 14528 existence sightings: the zero-length state is not exotic, it is the dominant state of a
just-created file.

## Change (candidate `88a90f9`, `scripts/test-ci-test-scope.py` only)

1. **Publish atomically.** Both fixtures (escape, flood) write `*.tmp` and `os.replace()` it into
   place — the convention `scripts/ci-test-driver.py`'s `write_summary` already uses — so no reader
   can observe a created-but-empty record.
2. **Consume content-aware.** New `wait_for_contract()` waits for a record that PARSES, bounded by
   the caller's deadline and by the command's own exit — instead of exiting its wait on `exists()`.
3. **Fail typed.** New `WitnessOutputError(AssertionError)` + `contract_record()`: absent, empty,
   and non-JSON records raise one named assertion failure carrying the command that produced
   nothing and its raw exit status. A bare `JSONDecodeError` from an empty parse is no longer a
   possible witness failure mode.
4. **Pin the contract on every host.** `WitnessContractTests` (4 tests; no Linux gate) — absent /
   empty / non-JSON → typed message with command + `raw_exit`; a late publication is waited for;
   a settled command without a record reports its exit; a live command fails at the deadline. Both
   former `json.loads(...)` call sites (the witness record and the flood `pids.json`) now go
   through the same helper.

## What I could NOT exercise (stated plainly)

- **The original flake was not reproduced by racing the pre-fix code in situ.** Its probability is
  the measured publication window over the 10 ms poll interval, so an in-situ reproduction is a
  lottery. Instead the mechanism was proven deterministically (the pre-fix reader body against the
  exact state `write_text` creates → the exact CI error string, raw exit 1), and the
  emptied-output case reproduces the failure mode on demand.
- **Hosted CI was not run at the pushed head.** The brief forbids opening a PR and this workflow
  runs only on `pull_request` / pushes to `staging`/`main`; the "same-head green" legs above are
  local (macOS) and remote-Linux runs of the exact step commands, not GitHub runners.
- **The Linux legs ran on Fedora 43 / Python 3.14.2**, not the hosted Ubuntu / Python 3.12 image.
  The exercised surface is `/proc`, `setsid`, `ps`, `signal` and `json`; no version-conditional
  code path is involved, and the new contract tests ran on both hosts.
- **`just ci` cannot mirror hosted CI's suite matrix.** The `rust-ubuntu-suite` job shards suites
  across 41 matrix jobs; `just ci` runs `cargo test --locked` once on the shared lane host under
  load from sibling lanes (1-minute average ~70 during this lane). Both runs happened to be clean;
  no load artifact was observed in either.
- The live acceptance sandbox (`~/.local/state/canter/`) was neither read nor written; no run was
  dispatched, paused, retried, released or resolved; no PR was opened and `staging` was not pushed.
