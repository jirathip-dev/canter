## The failing check, and what the reviewer measured

On the as-shipped release binary at the pinned head, `parse_supervision`
(`src/commands.rs`) placed the `--idempotency-key` rejection INSIDE the
`supervision arm` branch, so:

1. the usage text advertises `supervision arm --run RUN_ID [--idempotency-key
   IK]`;
2. `supervision arm --run … --idempotency-key <IK>` exits 2 with
   `supervision arm: --idempotency-key is not accepted (this subcommand is a
   read)` — a false statement about the surface, and the only path for the
   explicit key the usage line and the daemon contract
   (`params.idempotency_key`, `docs/contracts/spec-daemon.md:662`) advertise;
3. `supervision status --run … --idempotency-key <IK>` — the actual READ —
   silently accepts the flag.

## Reproduction (raw, BEFORE any change; release binary built from the pinned head)

`cargo build --release --bin canter` → exit 0
(`/tmp/c261-fixr1-logs/repro-build.log`).

Both reviewer facts reproduce exactly: the arm rejects its advertised flag

## The diff (one branch move in `parse_supervision`, `src/commands.rs`; net +3 lines)

The existing rejection `if` moved VERBATIM from the `supervision arm` branch
to the `else` (status) branch of the same `SupervisionAction` construction.
Nothing else changed: no test edited, no assertion deleted/widened/ignored/
made conditional, no new symbols. The arm's explicit key now flows through the
pre-existing path `SupervisionArmArgs.idempotency_key` (fallback
`fresh_run_key()`) → `supervision::arm_params` → daemon `journal_mutation`,
which already validates the `ik_` format typed (`refusal.malformed`).
