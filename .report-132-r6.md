## What this round delivers, and why it is the bounded change

Everything #132 names as unmet at the time the issue was filed is now
implemented and witnessed on the current integration base. Round 6 therefore
does **not** re-implement a landed fix. It closes the one item in this issue's
own lineage that is still open and still unwitnessed:

> **#169** — "Merge rehearsal: the ambiguous/timeout non-remap guard in
> `published_integration_head` is unwitnessed."

`published_integration_head` reads the published integration ref from the
checkout's `origin` (`git ls-remote`). An `origin` that answers with a failing
exit proves no base, so the read refuses this step's own unprovable-base code
(`effect.merge.failed`) and keeps the git diagnostics. But an **ambiguous** read
— one that never exits with a status (interrupted, timed out) — is *not* "not
readable": it must keep the outcome it already carries instead of being remapped
onto the unprovable-base code, so the class that produced it survives the step.
That guard was load-bearing and the only assertion of its **bypass** branch was
missing.

This round adds that witness as a test-only change: no production byte changes
(`src/` is untouched; `git diff --stat src/` is empty).

## The witness

`tests/mutation_engine.rs`,
`cycle2_ambiguous_published_read_keeps_its_own_outcome_and_is_never_remapped`:

- Real daemon, real git, disposable local repositories — the published-ref
  read is made ambiguous by a `git` shim on the scenario's allowlisted PATH
  that `SIGKILL`s itself for `ls-remote` and passes every other git call
  through to the real git. The read therefore never exits with a status: the
  ambiguous class the guard exists for.
- Asserted: the step's typed outcome is the read's own ambiguous outcome —
  `adapter.process_death` when the shim wins, `adapter.timeout` if the effect
  deadline reaps the read first — it is **never** remapped onto
  `effect.merge.failed`, the read's own diagnostics are preserved, and the
  integration checkout does not move.
- The same plan's EXIT routes (absent published ref, unreadable `origin`) stay
  covered by the existing
  `cycle2_rehearsal_refuses_an_unprovable_published_base_on_both_routes`.

## Why the issue's own acceptance criteria are already satisfied at this base

Checked read-only against `origin/staging` (`86313e8`) with the merged
implementation commits, not by re-running the whole acceptance:

- **A closed policy input** — `merge_inputs` requires
  `merge_policy: "squash" | "ff"` and refuses anything else
  (`src/mutation.rs`; `src/plan.rs` authors `p7` as `"squash"`).
- **Never a stale local view** — the merge step certifies the *published* head
  read from `origin`, refuses a checkout ahead of or diverged from it, and
  reconciles a strictly-behind delivery onto the fetched published head in the
  delivery's own worktree (`59a0a4c`, PR #182). The integration checkout's own
  ref is never moved.
- **`MERGE_NOT_FF` names the real cause** — the ff-policy divergence message
  ("a squash result is not an ff merge") and the unpublished/diverged local
  view message are policy-specific; the old "integration base moved after the
  review evidence was recorded" wording is gone.
- **A run completes on a squash-policy repository** — `post_merge_verify`
  accepts a squash landing by the same fail-closed content fact as the merge
  rehearsal, and `cleanup` proves the landing against the published ref when
  its own view cannot see it (`7a76495`, `c1581cd`; PRs #171, #183).
