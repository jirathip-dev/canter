### Why the pull-request route is the smallest correct shape

The repository's integration ref can only advance through a pull request, so
`p7` must publish through one. The route is DECLARED by the topology and never
inferred: an engine that silently fell back from a refused push into another
route would hide the refusal and break the plan-policy discipline of #196 (the
step's own published-ref target, #178 reconciliation, #202 frozen certified
head, the evidence gate and the closed `squash | ff` policy are all unchanged
and shared by both routes). The pull-request route consumes the delivery the
run's own delivery step already published — it never opens a pull request, never
invents a head — and asks the forge for the merge with that exact head matched,
then proves the landed content with the same fail-closed content fact the
landing, `post_merge_verify` and the cleanup proof use.

### New typed codes

| code | when |
| --- | --- |
| `effect.merge.push_rejected` | the remote REFUSED the pushed update by rule/protection (`push declined`, `repository rule violations`, `GH013`, a protected branch or a `pre-receive` hook) |
| `refusal.credential.missing` | the publish could not authenticate (git or forge) |
| `effect.merge.not_fast_forward` | the ref moved under the landing (pre-existing code, now also classified out of a failed push) |
| `effect.merge.publish_rejected` | the forge refused the merge, or the published ref does not carry the reviewed content |
| `refusal.publish.pull_request_missing` | the declared route has no OPEN pull request naming the certified head |
| `refusal.policy.publish` | the declared route cannot honour the step's plan policy (`pull_request` + `merge_policy: "ff"`) |
| `effect.merge.failed` | unchanged: only a genuinely unclassifiable local failure keeps it |
