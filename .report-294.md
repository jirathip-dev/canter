## 1. Preflight: what already landed at the base, and what still churns

The issue's C1 (a missing-but-registered worktree is refused instead of
repaired) is **already fixed at this base** — it landed as #282/#283 plus the
fix-lane half:

- `clear_stale_lane_registration` is called before the create at BOTH sites —
  `effect_worktree_create` (the p2/p4 lane) and `ensure_fix_lane` (the fix
  round's lane) — and the repair rides the outcome.
- Its witness is live at the base:
  `tests/review_dispatch.rs::a_missing_but_registered_reviewer_lane_is_repaired_and_the_review_proceeds`
  (deletes the checkout from under the registration, asserts the repair record
  names exactly `issues-5-rev1` and the review proceeds at the certified head).

The **residual defect** is C2+C3, and it is still live as of this lane's
preflight (read-only ledger reads, no writes):

```
idempotency (newest p6 rows)          status  outcome.error.code
run-3c68e508443d62c0  p6-258  22:30:31Z  spent  refusal.run.retry_bound
run-b57a1cabee4f3774  p6-261  22:33:42Z  spent  refusal.run.retry_bound
```

The first three p6 attempts of each run died on the (now-fixed) stale
registration (`adapter.exit`, git exit 128), spending the step's bounded
retries 3/3 (`run_retries` rows `rt_a7d0e073eb85e3b2` … `rt_6d9ee1d36b3315a8`
and `rt_ee6ba5af6ee4cd8f` … `rt_9d79114fe98224df`). After that, every check
re-derived the ONE continuation (#276's re-dispatch of the handoff's own step),
the engine refused it **before any effect** with `refusal.run.retry_bound`, the
daemon's in-memory ladder paced the attempts to its 900 s ceiling
(`DISPATCH_BACKOFF_MAX_SECS`), and the run re-applied the step forever while
reporting `running` with `eligible: true` — the measured ~15-minute churn.

## 2. The remedy: the continuation exists only while the run's own budget can pay for it

`src/supervision.rs`:

- `fix_redispatched_intent` now refuses to derive the re-dispatch when the
  shared per-(run, step) bounded budget is spent with no unconsumed
  authorization — the exact arithmetic the engine's own
  `refusal.run.retry_bound` refuses on (an unconsumed authorization is exactly
  the ONE dispatch it pays for, issue #241; below `RUN_RETRY_MAX` the engine
  can still mint one). Nothing is derived that the engine is guaranteed to
  refuse, so **no check re-applies the step** (AC2's "stops re-applying",
  AC5's "parks itself").
- The classification reports the exhausted shape with a NEW typed code,
  `supervision.fix_round_redispatch_exhausted` (class `needs-attention`,
  `eligible: false`), naming the fix leg's lane, the step, the **consecutive
  refused dispatches** the run's own records carry, the engine's own refusal
  code, and the certified head that still fails (`fix_redispatch_exhausted_detail`)
  — the run does not spin where nobody can see it (AC3). The human read renders
  `fix round re-dispatch exhausted: …`.
- The repair half stays exactly as the base shipped it: a lane whose
  registration is stale is still cleared and created at the certified head —
  never treated as "already clean" (the issue's bounds).

The park is a static-condition park, not a retry exhaustion that hides the
cause: an operator `run.retry` authorization is what re-opens the ONE
continuation later, and it is never required for the churn to stop (AC5).
Releasing/retrying the two witness runs stays operator control, exactly as the
issue's Bounds say.
