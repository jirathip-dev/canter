## What the gap was

A run that dies, is superseded, or merely expires keeps permanent ownership
of its issue. Measured symptoms reproduced as controls inside the new tests:

- a fresh submission for the owned issue is refused
  `submission.already_owned` (dead predecessor) or `submission.paused`
  (paused predecessor);
- the per-repository admission cap (`2`) stays spent on runs that can never
  progress, so an unrelated issue waits for capacity instead of being
  admitted;
- a run whose grant expired refuses `refusal.grant.expired` forever on its
  own recorded window, with no supported way to free it.

## What shipped

ONE new closed RPC method and ONE new CLI verb; no other surface changed.

- `run.release` (closed RPC set `39 -> 40`) / `canter run release --run
  RUN_ID --reason TEXT [--idempotency-key IK] [--socket PATH] [--config
  PATH] [--json]`, rendering the module-local `hf-run-release/v1` document.
- `State::release_run` commits ONE transaction: the run's unique
  `queue_ownership` row is removed, the run row goes `invalidated` with the
  pause state cleared and the resume digest consumed (so it leaves the OWNED
  status set and the counted occupancy set), and a hash-chained
  `run.release` audit record carries the operator reason, the exact run
  identity (repository/issue/revision), what was freed and the
  authorization window the run held.
- Typed, fail-closed fences: `refusal.run.in_flight` (a claimed `apply` of
  the run is in flight, or an unreadable claim's attribution is unknown),
  `refusal.run.retry_pending` (an unconsumed bounded retry authorization —
  it is never burned), `refusal.run.terminal` (a `done`/`invalidated` run;
  a same-key retry replays the recorded response instead of re-releasing)
  and `state.not_found`. A missing, revoked or **expired** grant is
  deliberately not a fence — that run is the case the release exists for —
  and the release records that window (`release.authorization.status` /
  `expires_at` / `usable:false`) without presenting or reusing it.
- A released run stays inert everywhere else: the engine refuses a terminal
  instance (`refusal.instance.state`), the control surface refuses
  `refusal.run.terminal`, supervision's dispatch intent returns nothing for
  it, and the delivered-evidence advance skips it. The freed issue is
  admitted by a fresh submission on its own merits, and the freed slot
  admits the issue that was waiting for capacity.

## Disclosures / limits (not verified, or deliberately out of scope)

- **Hosted CI was not run.** Gate evidence is local (`just ci`) only; the
  suite matrix in `.github/workflows/ci.yml` is unchanged because no new
  `tests/*.rs` file was added (the release battery extends the existing
  `tests/run_control.rs` / `tests/run_control_cli.rs` suites).
- **No release control in the Ratatui operator console.** The console's
  control surface still offers pause/resume only; the release is reachable
  through the CLI/daemon (the issue asks for "a first-class command with
  typed refusals"). The console's method table is untouched.
- **The alternative "rebind" half of the issue's parenthetical was not
  added as a new verb.** It already exists: presenting a LATER freshly
  issued grant window for the same binding in `queue submit` rotates the
  same run's window in place and records `grant.rotation` naming both rows
  (pinned by the existing
  `cycle2_expired_grant_rotation_continues_the_same_run_explicitly`). The
  release is the new path that makes an expired-grant run releasable; both
  are recorded, none of them silently reuses an expired window.
- **Interpretation of "the cap accounting must not be held by a run that is
  dead, released, or expired".** The counted set itself is unchanged
  (`new`/`running`/`human_queue`/`blocked`); the release is the operator
  path that removes a dead or expired run from it, and that effect is
  witnessed (a). Making the counting queries skip any expired run
  automatically would change ownership/capacity semantics globally
  (an issue would stay owned while its slot counted free) and was not done.
- **Pre-existing rendering inconsistency, not touched**:
  `render_human`'s control branch renders `boundary.reached` (a boolean)
  through the string reader, so `run pause` / `run status` print
  `boundary reached: unknown`. It predates this lane and is outside the
  issue's scope; the new release branch reads its `usable` flag with a
  boolean reader. Candidate follow-up.
- **The release's JSON success envelope** is exercised through the shared
  `ok_result` path; the CLI test asserts the human rendering of the release
  document (otherwise untested) plus the JSON refusal envelope and the JSON
  `run status` readback, because one fixture holds one releasable run.
- `just ci` does not run the standalone scripts
  (`check-contract-fixtures.py`, `test-build-archive.py`); this lane changed
  one entry in the first (the `run.release` id in its closed method set) and
  nothing that the second pins (no schema/chain change).
