## 1. The gap, read at the base (before any edit)

- `README.md` "Operating this" step 1 stops at `cargo build --release
  --locked`, so a built canter stays in `target/`. Nothing installs it to a
  stable PATH prefix, records the installed sha, reads `--version` back from
  the INSTALLED bytes, or keeps the previous binary for a one-step rollback.
- The pieces the issue's "Required shape" names already exist for a human to
  run — `canter config init|validate|show` (item 2) and `canter service
  doctor|install-plan|status-plan|uninstall-plan` (item 3), which render the
  first-party per-user launchd/systemd unit text and the exact host steps and
  "never install, start, stop, or query the host service manager"
  (`docs/OPERATIONS.md` §5.1, `src/service.rs`). Their execution is
  human-gated by the issue's own fence.
- `scripts/accept-bump.py` (issue #277) is not that path: it installs the
  acceptance target AND the launchd-supervised path and RESTARTS the host
  service, i.e. its step 4 is exactly what the fence excludes from a lane, and
  it is bound to the acceptance sandbox.
- Sequencing fact this lane rests on: a rendered unit's `ExecStart` is
  `std::env::current_exe()` (`src/commands.rs:7620`) — the unit launches the
  binary that RENDERED it, so installing the binary is a precondition of
  rendering the unit the service will actually run.

## 2. What changed

`scripts/install-canter.py` (new; operator tooling, stdlib only, no host path
baked in):

- **candidate** — `cargo build --release --locked` in `--checkout` (default:
  the current directory; the artifact resolves through `cargo metadata
  --no-deps`, so an out-of-tree `CARGO_TARGET_DIR` is honored) or a prebuilt
  `--candidate`. A dirty checkout refuses (`install.refusal.tree_dirty`)
  unless `--allow-dirty` records `source_dirty: true`; the built head is
  recorded from `git rev-parse HEAD`.
- **install** — stage the bytes beside the destination, RUN the staged copy
  (`--version`) BEFORE anything is replaced, retain the currently-installed
  bytes as `<prefix>/canter.previous`, replace `<prefix>/canter` atomically
  (`os.replace`), re-hash the destination and refuse
  (`install.refusal.install`) unless it equals the staged bytes — so the
  recorded sha256 is the identity of the bytes that answered the read-back.
- **record** — `<prefix>/canter.installed.json`: `schema
  "canter-install/v1"`, `action`, `acted_at`, `binary`, `binary_sha256`,
  `version`, `readback` (the full `--version` output), `source_revision`,
  `source_dirty`, `candidate`, `candidate_sha256`, `retained`.
- **rollback** — `--rollback` re-runs the read-back on the retained bytes,
  restores them, retains the replaced ones (the pair swaps, so the same
  command steps back again) and rewrites the record; nothing retained, or a
  retained file that does not match the record, refuses
  (`install.refusal.rollback`).
- **dry-run** — `--dry-run` prints the exact commands for install AND
  rollback and writes nothing.
- Never touches the service manager or the daemon. Typed refusals
  `install.refusal.{usage|build|candidate|prefix|install|readback|rollback|tree_dirty}`
  at exits 2/4/5/6/7/8/9/10; every failure path discards its staged files, and
  a refused read-back leaves the installed binary byte-unchanged.

`scripts/test-install-canter.py` (new; 82 checks, 84 with `--bin`): runs the
REAL driver against DISPOSABLE prefixes with fake candidates — the host's own
`~/.local/bin`, its service manager and its daemon are never touched, and the
suite needs no release build.

Docs: `docs/OPERATIONS.md` §10.2 (runbook: install → config → service →
rollback, plus the refusal table) and a §1 pointer; `docs/DEVELOPMENT.md` (the
driver and its self-test row, beside the issue #277 bump-driver section);
`README.md` "Operating this" step 1; `CHANGELOG.md` entry. Six files, +1120/−1
against `origin/staging`.

Nothing loosened: opt-in operator tooling beside `accept-bump.py`, run by hand
and never from CI; no CLI command, daemon surface, contract or gate changed,
and install execution stays human-gated.

## 6. Not verified (disclosed)

- The REAL host install is not executed by this lane: `~/.local/bin/canter`,
  the config for a real queue and the launchd/systemd activation are
  human-gated (the issue's own fence and this repository's contract), and the
  lane verifies the driver against disposable prefixes instead. AC1's "a fresh
  shell resolves to the installed binary" and AC3's "the restart survives a
  reboot" are therefore demonstrated mechanics plus the §10.2 runbook, not
  executed steps; AC4's dry run IS executed (transcript above).
- The lane never touched a live canter state store; pointing a config at the
  real topology is left to the operator (AC2).
- The rollback transcript above rolled back a lane-local disposable prefix,
  not a real host install (nothing real was installed); the hermetic suite
  additionally covers the swap and its refusal in every scenario.
- The new suite is operator-run (documented in `docs/DEVELOPMENT.md`), like
  the repository's other script self-tests; it is not wired into the hosted CI
  matrix, which would widen this change's contract.
