## 1. The defect (issue #260, residual NB-1)

The engine bounds BOTH the adapter ops one review step dispatches and its
verdict wait with the step's effective deadline (`effect_deadline_secs`,
`src/mutation.rs`): the `start` op, the `prompt` op and
`await_written_verdict` all take that one value. Four witnesses in
`tests/review_dispatch.rs` declared `deadline_secs: 1` *only* to make the
verdict wait expire inside the test, so one adapter call was also given a
one-second budget. A fork/exec that lost the scheduler race under the suite's
own 24-way parallelism was then cancelled inside its deadline, and the step
recorded the coarser `adapter.timeout` ("the operation exceeded its deadline
and was cancelled") instead of the typed `effect.review_timeout` the witness
pins — a RED on an untouched suite, which is what the issue reports.

Reproduced in this lane at this base, twice (w1, w2 in §3): 4 failed / 20
passed per run, the four fixtures the issue names; the same binary is green
serialized (w3). The precedent is `.report-225.md` §3 (w6a/w6e), which
adjudicated the same suite as an environment flake; #260 is the follow-up
that removes it.

## 2. The fix shape (bounded)

- The four declared budgets are now one named `WITNESS_DEADLINE_SECS = 10`
  (`tests/review_dispatch.rs`), with its reasons in the doc comment: 10 s is
  the repository's own bound for one bounded adapter call
  (`canter::adapters::ADAPTER_TIMEOUT`, 10 s), an order of magnitude above the
  worst fork/exec chain measured on this host, and it keeps the verdict wait
  these witnesses drive well inside the 30 s upper bound they pin.
- The no-verdict witness's lower bound now reads that declared window
  (`elapsed >= WITNESS_DEADLINE_SECS`) instead of the removed `1`, so it still
  proves the declared window was really waited. Its `elapsed < 30 s` bound
  (the wait is bounded, never a hang) is unchanged.
- **Assertions that changed** (AC3 asks which, and why) — exactly ONE existing
  assertion:
  `assert!(elapsed >= Duration::from_secs(1))` →
  `assert!(elapsed >= Duration::from_secs(WITNESS_DEADLINE_SECS as u64))` in
  `a_reviewer_that_writes_no_verdict_parks_the_frontier_with_a_typed_timeout`.
  It is re-pointed, not relaxed: the declared window it describes moved from
  1 s to 10 s, so it now asserts the same fact against the window the fixture
  actually declares, and w13 proves it still bites an engine that stops
  honouring that window. The budgets of FOUR fixtures changed from `1` to
  `WITNESS_DEADLINE_SECS` (the widening the issue's own "Wanted:" line asks
  for). ONE assertion was ADDED (NB-2, §5). NOTHING was deleted, skipped,
  renamed away or weakened.
- The engine is untouched: no `src/` line changed in the candidate commit.
- NB-2: the late-verdict witness now pins the recorded cleanup refusal `code`
  as the LITERAL wire string `refusal.lane.busy` — deliberately not the
  adapter's constant, which renames away with it — so altering the code
  string makes that witness RED (§5, w14).

## 6. Disclosed gaps / notes

- The widened budgets are a DELIBERATE cost, not a free win: the suite's
  serialized wall time grew from 52.76 s (pre-fix, load 10.10) to 113.94 s
  (load 20.74), because the three witnesses that wait for a verdict that never
  comes now wait 10 s each (and the re-attempt witness waits twice, where it
  waited twice at 1 s before). Hosted CI runs each suite through
  `scripts/ci-test-driver.py --suite=<suite> --per-suite-seconds 150
  --aggregate-seconds 180` with `--test-threads=1` — the serialized shape
  measured here — so the quiet-window figure is the pre-fix cell (48.7 s
  measured through the same driver in `.report-225.md` §3) plus the ~36 s of
  wait: roughly 85-90 s of the 150 s budget. On THIS host at load ~26 the
  serialized suite takes 113.94 s; a local run at a much higher load could
  approach that budget. The hosted cell at the delivered head is the
  authoritative gate and was not available to this lane (§ below).
- The 10 s budget is empirically backed, not proved: adapter WORK measured
  ~0.44 s inside a contended window (w7) while the base lost the race at a
  1 s budget in the same load band (w1/w2) — the loss is the scheduler stall
  in the fork/exec, not the work — and the fixed suite was 24/24 in every
  window measured up to load 31.1 (w5c). A host load far beyond 31 was not
  measured in this lane.
- The same one-second pattern exists in ONE suite outside this issue's scope:
  `tests/herdr_pane_execution.rs:906` also declares `deadline_secs: 1`. NB-1
  names `tests/review_dispatch.rs` only, and work is routed from its issue
  (`docs/WORKFLOW.md`), so it is reported here and NOT changed. It did not
  fail in any leg of this lane.
- The engine's own semantics are unchanged by this fix: a review step whose
  plan declares a one-second `deadline_secs` still gives its adapter ops one
  second (the reviewed #92 F1 contract). The issue asks for the fixtures'
  budgets to move, not the engine's rule, and that is what this lane did.
- A self-inflicted red, disclosed: the FIRST `just security` run at this
  report's commit was RED (`JUST_SECURITY_HEAD2_EXIT=1`,
  `RULE-ABS-PATH-UNIX	.report-260.md`) because the report's own prose quoted
  the scanner's absolute-home-path spellings verbatim. The prose was reworded
  so no rule literal appears in a tracked file and `just security` is green at
  the delivered head (`head2-fmt-security.log`, `JUST_SECURITY_HEAD2_EXIT=0`);
  the scanner and its rules were not touched, and no gate was bypassed.
- Not verified in this lane: hosted CI/Rust-macos jobs at the pushed head (the
  PR's own checks are the authoritative gate); `w7` is a measurement leg, not
  a witness (its failure is deliberate and its edit was reverted, sha256
  proved); the two parked runs named in the brief were not touched, and
  `canter daemon` / the acceptance state root / the queue were never invoked —
  every leg above is a `cargo`/`just`/`python3 scripts/*` command inside this
  worktree.
