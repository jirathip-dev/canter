## The defect and the chosen behaviour (carry forward)

The live ledger (read-only): run `run-486148bd1b3613a7` reached `p6-132` SUCCEEDED with its
verdict consumed and was **invalidated at 23:48:42Z**; the candidate rebuild's submission
(`qs_9534dc7e4b424b69`) bound a fresh run `run-03037c468003cd8b` at 23:48:44Z, which re-ran
`p1..p5` from scratch — so the committed tail (`p7` merge, `p8` cleanup) is never reached. The
mechanism is the revision-rebind admission (`admit_queue_item_in_tx`): a selected spec revision
different from the live owner's, authorized by a later grant window, atomically invalidated the
owner and bound a new run at its first step.

This lane chooses **option 1, carry it forward**: the rebind refuses while the owner's recorded
frontier has reached its own `review_evidence` step, and the run continues its own committed tail.

1. `src/supervision.rs`: `delivery_step_index` (the reviewed-evidence step of a committed spine,
   now shared with the existing `after_delivery_step`) and `frontier_reached_review(steps,
   frontier)` — the frontier is the review step itself or a step after it; an exhausted spine has
   reached it; a spine without a review step never matches.
2. `src/state.rs`: `owner_reached_review_frontier_locked` reads the SAME durable facts the
   driver's own frontier reads — the run's committed bound-input spine (the `request_line` of its
   admitted submission item), its recorded apply-attempt ledger, and `current_node` only as the
   pre-ledger fallback — so the submission path and the driver can never disagree about where a
   run stands. `admit_queue_item_in_tx` refuses the rebind (`submission.frontier_preserved`,
   naming the preserved run and the deliberate path) instead of invalidating the owner, and
   `State::run_reached_review_frontier` exposes the same predicate read-only.
3. `src/queue_preview.rs` + `src/queue_executor.rs`: the preview reports the same fact as
   `preview.frontier_preserved` (never the stale "no later grant window" claim), and the code
   joins the closed preview-hold mapping the submission consumes.
4. `docs/contracts/spec-daemon.md`: the rebind paragraph now states the carried-forward rule and
   the deliberate replacement path.

Replacing such a run stays possible — deliberately: the explicit, audited `run.release` control
frees its ownership and the run goes terminal, after which a fresh submission admits a new run
(its record names the reason, the freed ownership and the window the run held). The p7 merge
contract (#176), #194's landing semantics, #157 identity guards, #156 certification, #179/#180
bounded-retry semantics and `INSTANCE_STATE` are untouched: the change adds one refusal and one
preview hold and widens no cap, gate or budget.
