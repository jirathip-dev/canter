correct run can exceed a fixed budget purely because the machine is busy. That is the defect
this lane repairs: the ceiling is derived from the run's own machinery instead of from an
arbitrary number of seconds.

## 2. What changed — `tests/queue_advance.rs` only (no `src/` change)

`git diff --stat` against the branch point: `tests/queue_advance.rs` (251 insertions, 124
deletions) and this report file, nothing else.

- **`NO_PROGRESS_CHECKS: i64 = 24`** replaces `NO_PROGRESS_SECS: u64 = 120`. The ceiling is
  counted in the RUN'S OWN committed supervision checks, never in wall-clock seconds: the
  driver commits exactly one check per pass over a run, so the run's committed check count
  (`supervision.status` -> `evaluation.checks`) is the machinery's own progress clock and the
  gap between two committed checks is what this host actually needed for one pass.
- **`NoProgress`** (new) is fed each sample of a wait's own progress signature together with
  the run's committed check count and its in-flight step; it answers `Some(reason)` exactly
  when the ceiling passed. The ceiling is two-sided and BOTH sides are the run's own numbers:
  - the frontier may stand still across up to `NO_PROGRESS_CHECKS` of the run's own committed
    checks — the load-invariant form, because a slower host stretches the work and the tick
    that measures it by the same factor, so the number of passes a correct advance needs does
    not grow with load; and
  - the wall clock allowed is `NO_PROGRESS_CHECKS` x the cadence those checks are observed to
    take here (the newest observed gap between two committed checks), floored by the cadence
    the run's own recorded authorization declares — so a machinery that stops ticking
    altogether still fails after its own declared cadence, rather than never.
  The failure names the frontier, the passes observed, the cadence measured and the step in
  flight; it never names an arbitrary number of seconds again.
- **`CursorSample`** (new) is what `cursor_sample` returns: the frontier (run status, next
  step/kind, attempts) *and* the machinery clock (committed checks, in-flight step, recorded
  cadence) read from the same `supervision.status` document, so every repaired site feeds
  `NoProgress` the run's own numbers. The frontier signature itself is unchanged from
  #232/#295: progress is what the evidence MOVED the run to, never the tick count.
- **The ceiling never sits below the budget it replaces**: at the fixtures' declared 5 s
  cadence, 24 of the run's own passes is the same 120 s the old constant allowed; a slower
  machinery cadence grows the ceiling instead.
- **Four sites repaired**: the three `NO_PROGRESS_SECS` assertions (`:2420`, `:2796`, `:3405`)
  and the bare 120 s deadline in
  `the_daemon_consumes_only_the_head_the_runs_own_collection_certified`.

Not weakened: the waits still watch exactly the durable frontier they watched before (recorded
attempts, queue item status, certificate + newest evidence), and a stuck run still fails — §3(b).

  local rows show tolerance at the OLD budget rather than a grown one. The growing arm of the

- The same-second tie in the evidence ordering (`ORDER BY created_at DESC, evidence_id DESC`,
  `evidence_id` a content hash) is unaddressed: if a run's re-bound evidence ever lands in the
