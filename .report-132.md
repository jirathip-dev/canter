## What the issue asked, and what the base already had

#132's merged slices already shipped the policy *input* and the rehearsal
shape: `merge_policy` is a closed `squash | ff` step input, `effect_merge` is
a read-only rehearsal (`mode:"rehearsal"`, `landed:false`, no `merged_head`),
the refusal causes are split (moved base vs policy divergence name different
causes under `effect.merge.not_fast_forward`), and the built-in spine authors
`merge_policy:"squash"`. Three `cycle2_*` regressions cover never-lands,
squash-succeeds and ff-names-divergence.

One requirement of the issue was still unimplemented: "the run's `merge` step
must never leave the integration checkout diverged from the published
integration ref". The rehearsal read **only the checkout's own refs**, so a
bare-remote move was invisible until a fetch: it could certify a
policy-compatible result against an integration base the *published* branch
had already left, and the run then recorded an integration head its own next
`checkout` step cannot trust — the provenance drift the issue describes.

## The change

- `src/mutation.rs`: new `published_integration_head` reads
  `refs/heads/<integration>` from the checkout's `origin` remote
  (`git ls-remote`, so a bare-remote move is visible without a fetch);
  `effect_merge` refuses `effect.merge.not_fast_forward` before any policy
  check when the checkout's head disagrees with the published head, naming
  both heads ("fetch and re-review before merging"). An unreadable or absent
  published ref refuses `effect.merge.failed`: an unprovable base is never
  certified. Still no ref, checkout or remote mutation, and no new step
  params.
- `tests/mutation_engine.rs`:
  `cycle2_rehearsal_refuses_when_the_published_integration_ref_moved` lands
  the remote head from a second clone and asserts the refusal (plus the
  unchanged integration base).
- `docs/contracts/spec-plans.md`: the rehearsal bullet now records the
  published-ref proof and both refusal routes.
- `CHANGELOG.md`: entry for the change.
