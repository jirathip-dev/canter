## 1. The defect, as the issue states it (live RED, read-only)

A submission whose every selected item parked (`waiting` — the per-repository
slot was genuinely taken at submit time) has no run of its own that can ever
verify a delivery, so its #96 cursor can never move: the item reads `waiting`
with `consumed 0 · dispatched 0` forever while its recorded refusal reason
keeps naming lanes that finished hours ago.

Design in one paragraph: a verified delivery whose OWN committed submission
carries nothing left to dispatch continues the repository's next parked
submission instead of recording a bare exhaustion. Every committed submission
of the SAME repository that still parks an item is re-evaluated through its
OWN committed admission inputs (caps, occupancy attestation, grant, role
binding) with the SAME guard-verifying helper the submission, the #96 advance
and the #236 re-drive use; order is oldest submission first (`created_at`,
then `submission_id`), first `waiting` item in membership order. **At most ONE
item advances per delivery**; the consumption is recorded on the delivering
delivery's cursor row (`next_submission_id` names the submission whose cursor
the dispatch advanced), so the continued submission reads the same row through
`queue status --submission` — which delivery advanced it, and what it
dispatched (AC4's "the cursor must record what consumed it"). No second
delivery beyond the one that finds the item eligible is required. Every other
parked candidate is re-derived from live rows on every delivery reconciliation
(the hold that still applies — naming the CURRENT occupants — or
`queue.continuation_pending` when nothing refuses it but the delivery's one
advance was spent), so no item keeps a stale reason (AC3). A submission that
committed no `armed` authorization is never admitted
(`refusal.queue.supervision_unarmed`, issue #261), and a recorded hold that
named the winning item is settled by the dispatch that superseded it.

## 6. Disclosed gaps

- **AC2's live GREEN half is not deliverable from this lane.** The live daemon
  runs the released binary (schema v13); the parked item `qs_1145c6357c3c7bae`
  advances only once this fix is deployed and the next verified delivery is
  reconciled. What this lane proves is the live RED (read-only, §1) plus the
  fixture reproduction of the exact live shape and its GREEN (§3). The
  acceptance run's own p6/p7 and its post-merge drive are what demonstrate the
  live GREEN.
- **The read-time branch of AC3 is satisfied by the advance, not by a reader.**
  "Either it advances, or the reason shown is re-derived at read time": a
  cleared item advances (§3), and every other parked candidate's reason is
  re-derived from live rows on every delivery reconciliation — the engine's own
  trigger. `queue status` itself stays a pure projection of committed rows (no
  live capacity re-derivation at read time), because that read is the same pure
  function the submit response and the restart reconciliation serve and
  re-deriving it there would duplicate the one admission derivation.
- **Order is `(created_at, submission_id)`, oldest first.** With the live
  drive's per-issue submissions this is submission creation order; a batch
  submission's own membership order is unchanged (`first waiting` item).
- **A delivery whose own membership holds or dispatches an item never
  sweeps.** One delivery advances at most one item, and the advance it owes
  its own membership is spent first (the documented same-submission rule); the
  repository continuation runs only when that membership has nothing left to
  dispatch.
- **Cost**: one dry admission evaluation per parked submission per delivery
  reconciliation (plus one committing evaluation for the winner, and the
  post-admission re-derivation of the losers' reasons). Deliveries are rare
  (one per run) and parked submissions are few; the live shape measured 3.
- Ship-through: `Refs #324`; no direct push to `staging`/`main`; no gate
  bypass; no host paths, private repository names, credentials or model names
  in the added lines (scanner + gitleaks green at the delivered head).
