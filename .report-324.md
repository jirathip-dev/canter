## Root cause

`advance_queue_in_tx` (src/state.rs) recognized the delivery while the delivering run
was still LIVE: the real queue spine keeps its merge and cleanup after the
reviewed-evidence delivery (issue #152), so the run keeps its counted slot and the
repository's parked submission held for a genuinely-live reason. The delivering
delivery's own cursor row recorded a bare exhaustion (nothing of its OWN left to
dispatch). The exhaustion fence then early-returned on every later reconciliation of
the SAME delivery — including the reconciliation that completes the run and frees the
slot. Nothing else ever re-evaluates the parked item (an advance runs only inside a
delivery's own transaction), so the item waited forever on the stale text: exactly the
residual the spec names (advance never fires; reason replayed, not re-derived).

## The fix

The exhaustion fence now consults `delivery_completes_run` — the same #152 predicate
the completion write just below it uses — and falls through to the existing
`advance_repository_continuation_in_tx` sweep exactly when this reconciliation is the
one that completes the run. Prior guarantees unchanged: a run still live after its
delivery keeps the slot and the item keeps waiting; a recorded dispatch stays final;
a later delivery of the same delivering run is still spent.
