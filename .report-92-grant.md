## 1. The gap this closes (AC1)

Traced at the base: `State::issue_grant` (`src/state.rs`) had test-only
callers; `RPC_METHODS` (`src/schema.rs`) carried `grants.list` /
`grants.revoke` but no issuance method; the CLI had no `grant` verb. So
`canter board --plan FILE --grant REF=GRANT_ID` and the `apply` RPC bound to
grant ids that no supported caller could obtain.

The shipped mint path:

- **`grants.issue`** (closed method set `36 -> 37`): `params.grant` carries
  one `hf-grant/v1` document, `params.idempotency_key` the automation key.
  The document is validated BEFORE any journaling; an already-expired window
  refuses `refusal.grant.expired`; a production-class binding (phase
  `production`, or a `production`/`release` capability) refuses
  `refusal.policy.production_confirmation` (production authority stays
  human-only and this surface carries no confirmation channel). The intent
  (`mutate.grant.issue`) is journaled before the single row insert, and the
  response is the minted document in contract shape (`caps` as an array).
- **`canter grant issue --request FILE --issue N --expires-in SECS`** is the
  supported CLI caller over that method. Every field is DERIVED — repository
  identity and the issue's exact 40-hex acceptance revision from the reviewed
  bound-input document (`canter queue preview --out`), `workflow_hash` from
  that document's `workflow.hash`, `policy_hash` from its
  `role_config.revision` re-observed against the CURRENT configuration,
  phase/caps from its boundary, scope `worktrees/issues/N`, the live daemon
  epoch, and the explicit window; the grant id is content-addressed
  (`gr_` + sha256 of the canonical binding). Nothing is typed by hand and the
  CLI refuses a daemon response that does not match the requested binding.

No test-only seeding and no direct state write exists anywhere in the mint
path: it is the CLI -> socket -> daemon -> one row insert, and a mint without
a live daemon refuses `daemon.absent` (proved in `tests/grant_issue.rs`,
which also asserts the store stays empty).

## 3. Expiry proof (AC2) — `refusal.grant.expired`

- Refused at mint: a document whose `expires_at` is not in the future is
  refused with `refusal.grant.expired` BEFORE the claim (no grant row, no
  journal claim) —
  `an_already_expired_document_is_refused_at_mint_before_any_claim`.
- Refused at consumption (the typed code the contract names): a grant minted
  with `--expires-in 1`, consumed after it passed, yields an item verdict
  `refused` with reason `refusal.grant.expired` and no dispatched run —
  `an_expired_window_stops_being_consumable_with_the_typed_code`.

## 4. Epoch proof (AC2) — grants die with their epoch

- A presented document whose `state_epoch` is not the live epoch is refused
  `state.epoch_mismatch` with no row (`a_stale_epoch_document_is_refused_at_mint`).
- A state-epoch rotation (the real `backup.create` + `restore.begin` path,
  epoch 1 -> 2) invalidates the minted grant: it leaves the active set
  (`grants.list` empty) and its issue refuses as `refusal.grant.inactive`
  (`an_epoch_rotation_invalidates_the_minted_grant`).
- The live epoch is bound at mint time: `grant issue` reads the daemon epoch
  and a moved epoch refuses (`state.epoch_mismatch`); the re-observed role
  revision is checked before the wire, and a moved configuration refuses
  `refusal.profile.revision` with nothing minted
  (`a_moved_role_revision_refuses_before_the_mint`).

## 5. Authorization unchanged (AC3)

Issuance is not authorization and nothing on this surface authorizes a run:

- The board keeps the authorization point: `canter board --plan FILE --grant
  REF=GRANT_ID` (with the reviewed digest approval) is where a run is
  authorized; the mint response's own hint says so, and `board --grant`
  parsing/arming guards are untouched (`src/tui/**` byte-unchanged).
- Unknown-keyboard/back/cancel behavior is untouched (no `src/tui/**` edit);
  the CLI mint has no `--yes`-style blanket flag, no digest bypass and no
  prompt: the only inputs are the reviewed document, `--issue`, `--expires-in`
  and an optional idempotency key.
- A production-class binding refuses typed on both layers (CLI + daemon) —
  probe P2 disables both layers and the wire test goes RED, so the fence is
  real, not a single-layer gesture.

## 6. Atomicity, idempotency, crash points (AC4)

- Intent journaled before the effect (section 2); the claim machinery is the
  shared one (`mutate.grant.issue`).
- Exactly-once per idempotency key: same request id + key replays the recorded
  response byte-for-byte; a different request id reusing the key refuses
  `state.claim_reused`; the same binding with a fresh key refuses
  `state.grant_exists` (content-addressed id) — no second authorization for
  one reviewed run.
- Crash points (both tested with real daemon children, `CANTER_CRASH_POINT`):
  - `grants.issue.after-intent` (interrupted before the insert): after the
    restart the reconcile readback is `never committed`, `grants.list` is
    empty (no partial grant), and a retry with a fresh key mints cleanly.
  - `grants.issue.after-commit` (interrupted after the insert): after the
    restart the readback is `committed before the interrupt`, exactly ONE
    grant exists, and re-minting the same binding refuses
    `state.grant_exists`.
- A second daemon on the same state/socket is still refused (exit 1,
  `daemon.busy`) while the first daemon keeps minting
  (`a_second_daemon_is_still_refused_while_issuance_is_available`).
