## 1. The defect, and the mechanism decision

A run's **durably stored** admission profile document was written before #269
(`d4bf177`) made `skills` a key of the `hf-profile-binding/v1` material. The
run's own supervision presents that STORED document at every dispatch
(`state.run_role_binding` -> `params.profile` -> `ProfileBinding::from_doc`, the
`dispatch_at` path in front of `resolve_run_binding`), so the binding stopped
validating — permanently — and the run also holds an unconsumed bounded retry,
which closes the `run release` escape (`refusal.run.retry_pending`: a release
never burns an authorization). The two live runs therefore pin the
per-repository cap (2/2) with no operator-free way out.

Read-only measurements taken for this lane from the acceptance state store (no
write, no `run.*` control, daemon untouched):

- The STORED role binding of a parked run carries **no `skills` key at all**
  (exactly the pre-#269 document shape):

  ```
  {"configured_limits":{},"fallbacks":[],"introspection":false,"key":"<role>","kind":"hermes",
   "model":"<model>","provider":"<provider>",
   "revision":"4159d0ea4181ad726dbabf0612a8afd10115d4a2f433abb6435e7fe823d805d9",
   "schema":"hf-profile-binding/v1","secrets":[]}
  ```

- The same shape appears **one gate later**: the parked step `p6-…` is
  `review_evidence`, and its committed `params.reviewer_profile` is ALSO a
  pre-#269 document (no `skills` key, revision
  `93beff52fb63c1375fb00536794aa85e2bb0e38d00439c5104db03ce1ae231cd`). The
  review step's own param contract (`mutation::check_step_params` ->
  `review_evidence_inputs`) validates that document with the SAME decoder, so a
  fix that only covered the run's own binding would have moved the refusal one
  gate later instead of clearing it. This is why the change is one rule in the
  shared decoder rather than a rule at one call site.
- Both revisions are exactly `sha256` over the **pre-#269 material** (the same
  document without the `skills` entry, canonical bytes + trailing LF), recomputed
  out-of-band with the documented canonical rule and not with the code under
  test. The post-#269 fingerprint of the same material (with `skills: []`) is a
  different value, so a stored document cannot be re-fingerprinted into a
  revision it never carried.
- Both runs' latest audit rows are the loop the issue names
  (`supervision.dispatch_refused`, target
  `run-…:p6-…:refusal.profile.binding:reason:refusal.profile.binding: the
  profile binding requires skills (an array; may be empty)`, seq 1668–1675 at
  this read), along with `supervision.dispatch_backoff` ("1 consecutive refused
  dispatches; next attempt in 5s"), and both retry rows are `consumed_at` NULL
  (`rt_c6946cb6d6b0e504` attempt 2 / `rt_a7d0e073eb85e3b2` attempt 1).

**Mechanism chosen: remedy 1 (backward compatibility), and not remedy 2.**
Justification:

- The refusing documents are the product's OWN stored documents, and the shape
  already says the array "may be empty"; an absent key is the same material as
  an empty one. The fix is one rule in the one decoder that validates a
  presented document: an ABSENT `skills` key resolves to the empty array and
  its revision is verified against the pre-#269 material (the material that
  revision actually fingerprints). Nothing is weakened: a PRESENT `skills`
  value — string, object, bad key, bad pin, duplicate — still refuses typed, and
  a revision still has to fingerprint the material it binds, so no field can be
  smuggled in behind a claimed revision.
- It is the only one of the two remedies that reaches the acceptance's outcome:
  AC1 is "the two live runs' OWN supervision dispatch of `p6-…` no longer
  refuses". Remedy 2 (an escapable park) frees the SLOT but leaves the run
  refused forever — the run never resumes and the retry it holds is still never
  spent. Worse, "a retry that can never be spent" is only decidable while the
  binding refuses, so remedy 2 would have to encode that refusal as a permanent
  property of the run: a second rule for a state that does not exist once the
  first is fixed, plus a harder-to-verify predicate in the release gate (AC4's
  "a genuinely spendable authorization still makes `run release` refuse" would
  have to be re-proved against a new "unspendable" classification).
- Remedy 2 was **not** taken, so `run release` and its gate are untouched
  (`refusal.run.retry_pending` behaviour is unchanged — §4 witnesses it), and
  no operator control, migration or state write-back is involved anywhere.

## 2. What changed

| File | Change |
| --- | --- |
| `src/config.rs` | `ProfileBinding::from_doc`: an ABSENT `skills` key resolves to the empty array (only the absent one — a present value is validated exactly as before), verified against `legacy_revision_of()` — the fingerprint the pre-#269 product took (the canonical material with the `skills` entry removed). `material()` becomes "the material the binding's OWN revision fingerprints": a binding with no pins whose revision is that pre-#269 fingerprint hashes and re-serializes as the document it was approved from, so `revision_of()` still reproduces that revision and `to_doc()`/`to_canonical_text()` round-trip byte-identically. Both `from_doc`'s contract comment and the new private `material_with_skills()`/`legacy_fingerprint_of()` state the rule. |
| `src/config.rs` (tests) | `a_stored_pre_269_binding_is_dispatchable_and_present_values_stay_strict`: derives the pre-#269 fingerprint from the document it holds (never from the code under test), asserts the accepted binding keeps its revision and the round trip re-validates, and pins five present-but-malformed `skills` values as typed refusals. |
| `src/mutation.rs` (tests) | `a_stored_pre_269_reviewer_binding_passes_the_review_contract`: the review step's own contract accepts a pre-#269 `reviewer_profile` (the parked `p6` shape), the accepted document round-trips, and a present-but-malformed `skills` value still refuses at that same contract. |
| `tests/supervision_dispatch_refusal.rs` | `a_stored_pre_269_binding_is_dispatched_by_the_run_s_own_supervision` (+ `legacy_binding_doc` / `legacy_admission_scenario`): an armed run whose durable admission IS the skills-less document, with the topology recorded by the submission itself, so nothing but the run's own supervision dispatches a step of it. |
| `docs/contracts/spec-config.md` | The normative role-skills section states the backward-compatibility rule (absent key = empty array, verified against the pre-#269 material; present values unchanged). |
| `CHANGELOG.md` | `### Fixed (issue #279 …)` entry under `[Unreleased]`. |

No state migration, no durable write-back, no new control, no dependency, no
widening of any rule: one decode arm, the fingerprint it is verified against,
and the material rule that keeps an accepted document self-consistent wherever
the engine re-renders it (the review outcome's `reviewer_profile`, a stored
lane plan, `to_canonical_text()` at the replacement boundary).

## 4. No-regression witnesses (the other direction)

- **A present-but-malformed `skills` value still refuses typed** — five
  mutations (`string`, `object`, a non-slug key, a non-64-hex pin, a duplicate
  pin) refuse `refusal.profile.binding` in the unit test, and a present string
  refuses at the review contract too; all of them pass in GREEN and also under
  the §3.4 mutation.
- **A valid `skills` array still validates and yields the revision it does
  today** — `ProfileBinding::from_doc(binding.to_doc()) == binding` (new unit
  test), plus the pre-existing
  `profile_binding_documents_are_validated_and_revision_checked` and
  `profile_binding_preview_binds_the_reviewed_configuration`
  (`reparsed.revision_of() == binding.revision`).
- **A revision that does not fingerprint its material still refuses** —
  `refusal.profile.revision` for a pre-#269 document whose material moved (new
  unit test), and the pre-existing tampered/stale-revision cases.
- **A re-serialized document is always one the decoder accepts** — the accepted
  binding's `to_doc()` is byte-identical to the stored document and re-validates
  to an equal binding (new unit test + live probe), so the writers that re-render
  a validated document (the review outcome, a stored lane plan) cannot store
  something the next read refuses.
- **A genuinely spendable held authorization still refuses `run release`** —
  §3.5.
- **The parked runs, their lanes and their retry rows were not touched**: no
  `run.*` control was invoked against them and no `state.db` write was performed
  by this lane; the acceptance config and the daemon were left alone.

## 6. What I could NOT verify

- **The two live runs' resume is proven on a fixture and on their own stored
  bytes, never by dispatching them.** Those runs, their lanes and their retry
  rows are fenced off for this lane, so the acceptance's own supervision is what
  will actually re-attempt `p6-261`/`p6-258` after this change reaches the
  running installation. What is proven: the exact durable documents of both runs
  are refused by the pre-fix decoder and accepted by the fixed one (read-only
  probe, §3.1), the refusal they loop on disappears from a run of the same shape
  in a real daemon fixture with zero operator control (§3.2), and the accepted
  document stays self-consistent wherever the engine re-renders it. What is not
  proven: the live audit rows after the change, their supervision class
  transition, and the live cap freeing (AC1/AC3 are the acceptance run's to
  witness).
- **The cap freeing (AC3) is fixture-level too**: the witness here is that the
  run's own supervision dispatches its frontier instead of refusing it (its
  recorded attempt row succeeds and the frontier moves), which is the link the
  defect broke; the links after it — a held bounded retry being spent by the
  run's own re-dispatch, and a progressed run releasing its counted slot — are
  covered by the repository's existing witnesses (`tests/run_control.rs`,
  `tests/supervision_dispatch_refusal.rs`) and stay green in §5, but they are
  not re-witnessed by this lane on the live runs. No `queue preview` was run
  against the live installation from this lane.
- **`just ci`'s hosted-parity extras** (the policy checks the workflow adds on
  top of the local aggregate) are the hosted run's to confirm; the local
  aggregate is what this report records, with its raw exit in the log named
  above.
- **Cross-platform**: every gate above ran on this macOS host; the Linux legs of
  the hosted matrix are not exercised here.
