## Why (a2), and what happens on the NEXT bounded attempt

`p7` cannot re-certify by itself: a refreshed head that rewrites reviewed content is, by
definition, content **no verdict covers**, and the engine never invents a review round — the
committed review step (`p6`) has already succeeded, reviewer legs are never synthesised
(`refusal.evidence.reviewer_unbound`, issue #193), and the fix-round handoff (issue #238) is
driven only by a recorded review FAIL. (a1) would therefore mean building a NEW review round for
a merge-step outcome — a different, larger workstream than this bounded fix, and one the issue's
own remedy discipline (`refusal.delivery.moved`, issue #202: "the delivery must re-enter review
and a new verdict must name the moved head") deliberately leaves to the operator/lane side. This
lane implements (a2): park typed, retries unspent, remedy named.

**What happens on the next attempt.** There is no automatic next bounded attempt: the code is in
the unspent-park set (`src/supervision.rs:911`), so supervision derives **no dispatch intent** for
it and the run parks with `0/3` consumed (the live run in the issue burned `3/3`). A permanently
mismatched delivery therefore cannot exhaust the budget on this condition by itself. If a
re-dispatch is attempted anyway it stays fenced like every diagnosed step, and the retry is
deterministic: the withdrawal restores the exact pre-attempt state, and the replay is a pure
function of (delivery head, published head, fork point), so an authorized attempt re-derives the
same divergence and refuses **identically** — the budget is never "spent on the condition" in any
way that changes the outcome. (The daemon's diagnosed-step fence is existing behaviour and is not
re-witnessed here; the supervision park is.) The remedy the refusal names is the supported
recovery: refresh the delivery against the current published head under a fresh review and let a
**new verdict name the refreshed head**; the same step then sees `branch_head ==
certified_head` and consumes it under the ordinary landing path (including the hosted-check gate
it already carries).

That is acceptable because both alternatives are worse: certifying unreviewed replayed content
would merge content no review covered, and re-dispatching the same step only re-derives the same
refusal while burning the budget — the measured #263 defect.
