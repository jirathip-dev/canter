## 1. The defect, as measured

Every completed run left its reviewer lane behind. At the instant the verdict
is consumed the reviewer's own turn is still `working` (it has just written the
verdict), so the single close refused and the refusal was recorded — 30 of 30
recorded p6 receipts (2026-09-19..2026-09-25) carry exactly this shape:

```
workspace: {closed: false, code: "refusal.lane.busy",
            message: "lane rev-231-r1 is still working; preserve its workspace"}
checkout:  {removed: false, skipped: "the lane workspace is still held; the checkout is preserved"}
```

Nothing ever retried it, so the registration, the pane and the checkout outlived
the run, and the next run of the same issue refused
`refusal.lane.name_collision` until an operator closed the workspace by hand
(the #224 run spent three bounded retries on it).

## 2. Root cause (base-commit code locations)

- `src/mutation.rs` `remove_reviewer_lane` — ONE `close_lane_workspace` call,
  judged from a single read taken milliseconds after the verdict was written,
  i.e. while the reviewer's turn is still live. Called from exactly one site:
  the verdict consume of the `review_evidence` (p6) effect for
  `ExecutionMode::HerdrPane`.
- `src/mutation.rs` `effect_cleanup` (p8) reclaims the **implementer**
  worktree and branch only (`cleanup_inputs`), so the reviewer lane's checkout
  is nobody's residue once the verdict is consumed.
- `src/daemon.rs` `method_apply` resolved the run's issue's ledger-terminal
  generations only for `harness_start`/`worktree_create`. On
  `review_evidence` the effect's own reclaim loop (`ensure_reviewer_lane`,
  which reclaims a LEDGER-TERMINAL generation's reviewer lane and was landed by
  issue #190/#210) therefore ran against an **empty set** — the reviewer-leg
  bind presented no authority at all, which is why the pre-existing orphans
  refuse the successor's bind.

## 3. What changed

- **`src/mutation.rs` — settle-then-close at verdict consume (AC1, AC4).**
  `remove_reviewer_lane` now runs the close under
  `await_settled_lane` — the cleanup step's own bounded lane-settle wait,
  reused verbatim (issue #170 N7 discipline: `COLLECT_STOP_SAMPLES` consecutive
  corroborated read-backs, both views non-working, the lane's lifecycle counter
  unmoved, sampled across `COLLECT_STOP_INTERVAL_SECS`) — bounded by the step's
  own effective deadline (`effect_deadline_secs` of `review_evidence`, i.e. the
  plan's declared `deadline_secs` or `REVIEW_DEADLINE_DEFAULT_SECS`). A lane
  that starts working again between the confirmation and the close voids the
  confirmation and the wait re-confirms; a typed refusal that is not the busy
  timing condition returns at once, never waited on; an unobservable lane
  carries no settle evidence and goes straight to the close.
  `await_settled_lane` gained one parameter (`outlived`) so the park's sentence
  names what the waiting step outlived — p8 keeps
  `LANE_OUTLIVED_PUBLISH`, p6 uses `LANE_OUTLIVED_REVIEW`.
  The receipt keeps the **close's own last read verbatim** (`closed`, `code`,
  `message` — a still-working lane still records its `refusal.lane.busy`, the
  #260 NB-2 pin, so NO landed assertion moves) and records the wait beside it:
  `waited_ms`, plus a `wait` block (`bound_secs`, `code`, `message`) carrying
  the `effect.lane_timeout` park when the bound expires. The step still
  SUCCEEDS with its receipt either way — no bounded retry is spent and no run
  parks on the timing (AC4).
- **`src/daemon.rs` — the reviewer-leg bind resolves the terminal set (AC2,
  AC3).** `lane_binding_step_kind` is the ONE place naming the bind kinds
  (`harness_start`, `worktree_create`, `review_evidence`) and
  `resolved_lane_generations` is the ONE place resolving them from the run
  ledger (`State::retired_run_ids` — `invalidated`/`done`, scoped to the run's
  own repository issue, never read back from the substrate). With the set
  presented, `ensure_reviewer_lane`'s existing ownership-verified reclaim
  retires the previous generation's registration and clears its stale checkout
  (both recorded on the step outcome as `retired_reviewer_lanes`) and the
  successor binds at the certified head. A live or foreign holder is never
  adopted: the collision refusal stands verbatim (AC3), unchanged.
- **Docs/CHANGELOG:** `docs/contracts/spec-review-evidence.md` (item 3: the
  bind resolves the terminal set; the removal waits), `docs/contracts/spec-capabilities.md`
  (the #190 bullet names the bind kinds), `CHANGELOG.md` (Unreleased).

## 6. What I did NOT verify (residual risk)

- **No end-to-end daemon-socket witness for the reviewer-leg reclaim.** The
  daemon's resolution is pinned by the unit tests of §4.5 (a real ledger row
  set, the closed kind set) and the effect-level reclaim by §4.4, but no test
  in this lane drives a `review_evidence` `apply` through the real socket with
  a reviewer-lane fixture. A socket-level witness would need a review-dispatch
  fixture over the real daemon (there is none today).
- **The wait's wall-clock cost in production.** A reviewer lane that never
  settles now costs the step's effective deadline (default 1800 s, plan's
  `deadline_secs` when declared) before the receipt parks — the same bound p8's
  cleanup already uses for the identical timing condition. Only the
  `long-turns`-style stuck turn pays it; the common case costs the confirmed
  settle (~15 s).
- **The 30 existing orphans' actual panes were not touched**: this change makes
  the NEXT run of each issue reclaim them (AC2); it does not sweep the
  already-registered residue of runs that will not run again.
- **`just security` ran on this host with this host's `gitleaks`/`cargo-deny`
  versions** (prerequisites per `docs/DEVELOPMENT.md`); hosted CI parity is the
  PR's own checks.
