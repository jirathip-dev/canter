## The claim under test

`src/mutation.rs` `lane_integration_base` (as landed, line 2609) resolves the
observed/published integration base with a fetch plus `cat-file` fallback, so
`worktree_create` no longer derives the lane base from the stale local branch.
The measured code path is the real one: `method_apply` in `src/daemon.rs`
builds the `EffectContext` and calls `crate::mutation::execute_step`, which
routes `worktree_create` to `effect_worktree_create` → `lane_integration_base`
→ `published_integration_head` (`git ls-remote origin refs/heads/<branch>`)
plus the `cat-file -e` probe with the `fetch origin <branch>` fallback. The
refusal path is `published_integration_head`'s fail-closed mapping of an
unreadable `origin` to `effect.merge.failed`.

## The discriminating witness (what was built)

`tests/mutation_engine.rs` (+114 lines, witness commit above), two focused
tests run over the repository's real daemon binary and socket fixture with
disposable local repositories:

- `verify164_lane_base_is_the_published_head_not_the_stale_local_branch` —
  builds the defect shape: a sibling clone publishes a commit to the local
  bare `origin`, so the checkout's LOCAL `staging` is behind while the
  PUBLISHED ref is ahead, and the published commit is **absent from the
  checkout** (asserted before the run: `git cat-file -e <published>^{commit}`
  fails), so the fetch + `cat-file` fallback is really exercised. The first
  `worktree_create` (no recorded observation) must derive the lane base from
  the published ref.
- `verify164_unresolvable_published_base_refuses_fail_closed` — the refusal
  leg: no recorded observation, the checkout's `origin` points at a path that
  is not a git repository (the published ref cannot be resolved at all), while
  the stale local branch still exists. The step must refuse fail-closed and
  create no lane from the unprovable base.
