# Issue #307 — an interrupted in-flight claim resumes without charging the run's bounded retry

## The defect, read from the recorded rows

The restart reconciliation resolves every claim it finds in flight as
`ambiguous`. For an `ambiguous` resolution the daemon-owned outcome builder
(`daemon_outcome` in `src/daemon.rs`) dropped the typed error it was handed, so
the recorded attempt carried no code at all. The ONE diagnosis predicate behind
the bounded-retry fence (`state::step_attempt_diagnosed`) read a recorded
`ambiguous` attempt as a step failure, so the next supervision pass fenced the
step, minted a bounded authorization (`run_retries`) and re-dispatched it — one
retry charged to the run for the daemon's own restart. That predicate is also
what the daemon's supervised-dispatch decision, the driver's eligibility, the
`run status` retry disposition and the #285 terminal-by-outcome capacity read
key on, so each of those read the interruption as the run's own failure.

The asymmetry the fix closes: the apply executor's reaper already recorded the
SAME interruption fact with its code (`state.interrupted`, pinned by the
daemon's own unit test); only the boot reconciliation dropped it.

## Witness (committed)

`src/daemon_retry_tests.rs::a_restart_interrupted_claim_reconciles_without_charging_the_runs_bounded_retry`

Drives the REAL pieces: a step apply claim is journaled and left in flight
(the measured shape — "the first attempt simply never resolved"); the daemon's
OWN `reconcile_claims` runs (the same function `serve` calls before it accepts
requests); then the real supervision driver and the real apply path resume the
step. Asserted:

- the reconciled claim is `ambiguous` and its recorded outcome carries
  `state.interrupted`; the `reconcile.apply` journal row is its own record;
- the run's retry ledger is EMPTY — the resume charges 0 retries — and the
  driver's intent for the step is the plain continuation (`DISPATCH`), not a
  park and not a retry;
- the interrupted effect resolves once, typed and journaled (`p2` recorded
  `ambiguous` once, then `succeeded`), and the run's last achieved step is the
  resolved one;
- the SAME fixture's next diagnosis the run owns (`effect.review_timeout`)
  still spends exactly ONE bounded retry, consumed by the dispatch it pays for
  — attempt 1, so the interruption never counted against the shared budget.
