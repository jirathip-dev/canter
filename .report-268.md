## 1. What the issue asked, and what this slice lands

The issue measured one `SupervisorCore::pass` at ~16.4 s CPU across a ~20 s
wall window (two/three armed runs, once per 60 s tick) with the whole cost
inside `SupervisorCore::pass → recorded_worktrees_root →
State::run_dispatch_context → State::supervision_evidence → Val::parse_json`,
and required four things. All four land here; nothing else changed.

1. **Parse each run's recorded evidence once per pass.** The run's recorded
   control rows are now selected by the run's own durable identity in SQL and
   parsed exactly once into `RunRecords` (`src/state.rs`). Every reader of that
   run — the recorded dispatch context, the certified delivery, the
   dispatch-context presence check, the attempt ledger and the recorded fix
   round — derives from that one read, and the driver's pass hands the same
   read to both the evidence snapshot and the recorded worktrees root. Before,
   each of those five reads scanned the whole idempotency journal and parsed
   every request/response line for itself, per call site.
2. **Bound `recorded_worktrees_root`.** It no longer scans (or parses) an
   unbounded record set: it reads the rows the run names once and derives the
   root from that same read (`recorded_worktrees_root_of`, `src/supervision.rs`),
   and the public `recorded_worktrees_root` is that derivation over one bounded
   read.
3. **State the measured before/after** — section 2, with the raw stamps.
4. **Do not weaken classification**: no evidence read is skipped, nothing is
   cached across reads (each read is a fresh SQL read of the rows its caller
   names), no dispatch gate or classification input changed — section 3.

The identity predicate is the same predicate the parsed readers applied in
Rust, evaluated by SQLite against the recorded JSON (`json_extract` of
`params.instance_id`, and the digests of the submissions that admitted the
run), so the formatting of a recorded line never decides whether the run reads
it (witness: section 3.1, third test).

## 3. Classification is not weakened (AC2)

### 3.1 The witnesses (`tests/supervision_reparse.rs`, new)

Driven through the REAL driver (`supervision::start` over real state, real
supervision rows, 1 s check interval) and observed only through durable facts
the pass itself committed (`last_check_class` / `last_check_reason` /
`last_check_trigger` / `checks`) or the dispatch intent the check handed the
dispatch hook.

- `the_next_tick_classifies_the_evidence_recorded_since_the_last_one` — the
  boot pass classifies an untouched frontier (`healthy` /
  `supervision.dispatch.next_step`, trigger `boot`) and dispatches `p1`; a
  NON-succeeded attempt for that step is recorded BETWEEN ticks; the next tick
  (trigger `timer`, `checks` 1 → 2, ~1.0 s later) classifies
  `worker-timeout` / `supervision.worker_timeout` from the NEW evidence and does
  not re-dispatch the diagnosed frontier. The same read carries the raw message
  recorded between the ticks (`last_failure.message`).
- `a_settled_worker_moves_the_frontier_on_the_next_tick` — a worker that
  SETTLES between ticks (`p1` recorded succeeded) is classified on the next
  tick and the check's own dispatch intent moves from `p1` to `p2` (frontier
  responsiveness unchanged).
- `the_read_takes_the_runs_own_rows_and_nothing_else` — the run's OWN recorded
  rows are read (topology, admission attestation, integration base, the head
  its own collection certified, the attempt ledger), including a row whose line
  is NOT canonically formatted (reordered keys, spaces) and a row whose line is
  not JSON at all (which the parsed readers skipped and which must not turn the
  read into an error) — while a foreign run's rows, which present a CONFLICTING
  topology and their own failure code, are never read as this run's (positive
  control: the same foreign rows ARE read as the foreign run's own).

### 3.3 What the read still takes, and what it never caches

`RunRecords::read` runs a single query per read:

```sql
... FROM idempotency i
 WHERE i.outcome IS NOT NULL
   AND ((i.method IN ('apply', 'run.resolve')
         AND (CASE WHEN json_valid(i.request_line)
                   THEN json_extract(i.request_line, '$.params.instance_id') END) = ?1)
     OR (i.method = 'queue.submit'
         AND (CASE WHEN json_valid(i.request_line)
                   THEN json_extract(i.request_line, '$.params.digest') END) IN (
              SELECT s.digest FROM queue_submissions s
               WHERE s.submission_id IN (
                     SELECT item.submission_id FROM queue_submission_items item
                      WHERE item.instance_id = ?1 AND item.status = 'admitted'))))
 ORDER BY i.rowid
```

- The predicate is a SUPERSET of the predicate the parsed readers applied
  (`params.instance_id` equality for `apply`/`run.resolve`; submission
  membership by digest for `queue.submit`), and the Rust-side checks are
  unchanged, so no row a reader used to consider is lost.
- An unreadable/unparsable line is skipped exactly as the parsed readers
  skipped it; an empty response stays "no response".
- Row order (`ORDER BY rowid` ascending) and per-reader method filters are
  preserved, so the "newest recorded" semantics of each reader are unchanged.
- Nothing is memoized across reads: every read re-queries and re-parses the
  rows the caller names, so a verdict can never be served from evidence that
  moved since it was read.
