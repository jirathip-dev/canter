## The gap the issue names, and the behaviour this lane ships

The issue records — with its own correction — that the observed invalidation of the acceptance
spine's runs was each preceded by an explicit, recorded `run release`, so the literal "silent
supersession" is **not** witnessed; what the evidence supports is a **missing guard in the
submit path**: nothing there stopped a submission from taking an issue whose run was live. The
mechanism is the moved-revision branch of `admit_queue_item_in_tx` (a selected spec revision
different from the live owner's, authorized by a later grant window): it **invalidated the
incumbent** and bound a fresh run at `p1`, which is exactly how a live `p5` frontier can be
discarded.

| Submit shape | Before | After |
| --- | --- | --- |
| same revision, live owner, no resume authorization | `submission.already_owned` | `submission.already_owned`, message names the live run **and its frontier** |
| moved revision, later window, owner NOT past review | **owner invalidated, new run bound** | **`submission.live_run`** — refused typed, naming the live run and its recorded frontier; owner untouched |
| moved revision, later window, owner AT `review_evidence` frontier | `submission.frontier_preserved` (#192) | unchanged, message names the recorded frontier |
| moved revision, older/equal window | `preview.revision_stale` | unchanged |
| live owner, no later window | `preview.revision_stale` | unchanged |
| same revision, EXPIRED window + later window | `grant.rotation` (same run continues) | unchanged |
| after an explicit, audited `run.release` | fresh submission admits a new run | unchanged |

The frontier named is the run's **recorded** frontier, read from the same durable facts the
driver's own frontier reads: the frontier step with its kind from the committed bound-input spine
plus the recorded apply-attempt ledger (`current_node` only as the pre-ledger fallback), and the
run's recorded supervision class — the class of its newest committed check, `unknown` before the
first check. That is the same value `supervision status` reports as `evaluation.class` (a
recorded read, never a read-time re-classification).
