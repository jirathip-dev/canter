## Cause and contract

Both local base reproductions failed the named supervisor-tail test. The
fixture daemon recorded the actual failure before the 90-second assertion:

```text
step m1: adapter.exit: git ... exited with code 128:
fatal: 'origin' does not appear to be a git repository
fatal: Could not read from remote repository.
```

PR #156 added published-integration-ref certification; the fixture introduced
by #153 supplied only a local repository, with no origin. The failure is not
in #154 or #158. No change to either of those branches was investigated or made.

The product contract at the pinned base is internally consistent:

- `src/mutation.rs:2894-2919`: `published_integration_head` reads
  `origin`'s `refs/heads/<integration>` using `git ls-remote`.
  `effect_merge` at lines 2951-2967 refuses an unprovable or differing
  published head before the policy rehearsal.
- `src/supervision.rs:254-267`: the driver may run merge/cleanup only as the
  authorized committed tail behind verified delivery. `dispatch_intent` at
  lines 684-722 also checks the latest attempt (710-715): an already-attempted
  step belongs to the operator, never to automatic redispatch.
- `src/run_control.rs:733-749`: the frontier is the first committed step
  whose latest attempt is not succeeded.
- `src/state.rs:11924-11951`: `delivery_completes_run` requires the latest
  attempt of every committed successor of the delivery to have succeeded.
  `advance_queue_in_tx` writes `done` only under that predicate at 12071-12077.
  `advance_instance` at 3463-3501 writes running/human_queue/blocked, not done.

Therefore the old fixture correctly stayed live at its failed merge, owing
merge and cleanup. Allowing completion, bypassing published-ref certification,
or retrying the failed effect would be the wrong fix.
