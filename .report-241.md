## 1. The defect and the fix in one paragraph

`run retry` recorded a single-use bounded authorization (`run_retries`) for one
diagnosed frontier step, but nothing consumed it: `supervision::dispatch_intent`
returned nothing whenever an unconsumed row existed ("a pending operator
authorization reserves the step for the operator's corrected dispatch"), so the
run stayed parked behind a human hand-dispatch while `run release` refused
`refusal.run.retry_pending`. The fix makes the authorization effective: the
armed driver derives its continuation intent for a frontier that HOLDS an
unconsumed authorization, and the daemon's supervised apply path consumes that
row in one write under the dispatch's own journaled idempotency key.

## 2. Which component consumes it, and how the consumption is recorded (brief item 1)

- **Intent**: `src/supervision.rs::dispatch_intent` — a held authorization is a
  disjunct of the diagnosed-step arm (`authorized && !tail`), so the intent is
  derived for exactly that step and handed to the daemon's dispatch hook.
- **Consumption**: `src/state.rs::consume_supervised_retry`, called from
  `src/daemon.rs::method_apply_from` (the supervised apply path) after the
  intent's claim is journaled and before any effect. It consumes the HELD row in
  place (`UPDATE run_retries SET consumed_at, consumed_key WHERE retry_id = ?
  AND consumed_at = ''`) and only mints a new row when none is held (the
  automatic retry of issue #179, unchanged).
- **Record**: `run_retries.consumed_at` + `consumed_key` = the dispatch's
  journaled idempotency key (`ik_run-<run>-<step>-<unix>`), plus the apply
  claim/outcome in `idempotency` and the hash-chained audit journal. A replayed
  request (same key) replays the recorded response; a DIFFERENT dispatch of the
  same step finds no unconsumed row and refuses `refusal.run.retry_required`
  before any effect (single use).
- **Boundary kept (issue #152)**: the risk-classed committed TAIL
  (`merge` / `cleanup`) keeps its rule verbatim — an ATTEMPTED tail stays the
  operator's, and a held authorization over it is spent by that operator's own
  `run dispatch` (the release refusal names exactly that remedy). Witnessed by
  the untouched
  `tests/queue_advance.rs::the_supervisor_dispatch_capability_for_the_committed_tail_is_typed_and_closed`
  (green).

## 4. `supervision status` distinguishes the three dispositions (issue AC4)

`evaluation.retry` (new, read-time, additive to `hf-supervision/v1`) reports the
frontier step's retry disposition from the same durable rows the engine's fence
reads — `awaiting-authorization` / `authorized-awaiting-dispatch` /
`driver-dispatch` / `exhausted`, with `step`, `consumed`, `bound`; the human
render prints `retry <disposition>: step <step> (<consumed>/<bound> consumed)`.
A refused continuation keeps its own `evaluation.refusal` read
(`supervision.dispatch_refused` with the engine's own code and reason).
Witnessed by `retry_redispatch_carries_the_operators_corrected_params` (daemon +
CLI, green): `awaiting-authorization` before `run retry`,
`authorized-awaiting-dispatch` after it.
