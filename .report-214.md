Two facts follow from the engine's OWN code at the base, not from inference:

1. attempt 1 must have **proven the prompt delivered** — `review_self_dispatch`
   returns the prompt op's outcome BEFORE the verdict wait, so a recorded
   `effect.review_timeout` can only be reached after
   `delivered.status == "succeeded"` (the #148 kick + read-back);
2. attempts 2 and 3 could not re-prove a delivery — while the reviewer's first
   turn was still running the substrate cannot take a second submission inside
   the prompt's bounded delivery window (herdr 0.9.0: an accepted submission
   whose working/blocked state is not observed inside its own 5 s window is
   `agent_prompt_stalled`, a closed transient code the engine retries until the
   window expires — the row message above). The engine reported the PROMPTED
   leg as "the prompt was not delivered", spent the bounded retries on it, and
   the re-attempts **cleared the verdict path before each re-prompt**, so the
   verdict the reviewer went on to write (05:27:56Z) could never be consumed.

That is the non-convergent state machine the issue names: ambiguous timeout →
false "undelivered" → retry → … → `retry bound 3/3 consumed · progress frozen
· needs-attention`, while the only real next step (consume the same leg's
verdict) needed an operator kick.

- **Delivery ledger.** After a PROVEN delivery (`delivered.status ==
  "succeeded"`, i.e. the #148 read-back pair: the task text arrived AND the
  agent's lifecycle moved) the engine records `hf-review-delivery/v1` beside
  the verdict artifact — `<state>/reviews/<lane session>-<step id>.delivery.json`
  — carrying the certified head, the reviewer lane, the adapter-verified agent
  and pane, and the submission attempt count. The document is published
  atomically (staged + renamed; the #186 lesson). It is written ONLY after a
  proven delivery, so trusting it is trusting a proof, never a spawn.
- **Resume, never re-deliver.** Every dispatch of the step addresses the SAME
  derived leg (#210): when the start REUSES that leg's registered lane
  (`result.reused`) and the record is bound to THIS certified head and THIS
  reviewer lane, the attempt skips the residue clear, the re-prompt and the
  re-proof, and resumes the bounded verdict wait. A fresh lane, another lane
  round or a moved head is never trusted: that attempt re-delivers and
  re-proves as before. The bare-subprocess substrate has no asynchronous leg
  (its prompt IS the reviewer's run), so it always re-delivers and never reads
  a record.
- **The late verdict survives.** The residue clear now runs only on the
  delivery path, so a legal verdict already at the daemon-owned path is
  consumed by the resumed wait (validated exactly as any verdict:
  `verdict_stale`/`verdict_malformed`/`verdict_pending` refuse it, unchanged).
- **Fail closed.** A record that EXISTS but cannot be read, and a proven
  delivery that cannot be recorded, refuse
  `refusal.evidence.review_delivery` — never a silent re-prompt on a guess.
- **Observability (W4).** The recorded step outcome additionally names the
  reviewer's pane (`reviewer_pane`), its serving model (`serving_model`, the
  registry-resolved binding the reviewed plan bound and the leg is launched
  with hermes `--provider … -m …`; the adapter read-backs carry no model
  footer, so this is the recorded resolution, never an observation) and the
  delivery attempt count (`delivery_attempts`, the adapter's own count, or the
  recorded count when the delivery was proven by an earlier attempt). The
  ambiguous `effect.review_timeout` outcome carries the same facts in its
  MESSAGE — the durable `hf-outcome/v1` drops `result` for a non-succeeded
  effect (`apply_outcome`), so the message is where a stuck leg must be
  diagnosable from.
- **No constant moved.** `git diff cce8674..HEAD` touches no
  deadline/freshness/window/retry-bound constant (grep for
  `DEADLINE|deadline_secs|RUN_RETRY_MAX|WINDOW_MS|freshness` over the diff:
  exit 1, no match).

## Disclosed gaps (what this lane did NOT prove)

1. **W1's driver leg is composed, not single-process.** The witness drives the
   two dispatches of the review step directly (the same `execute_step` path the
   daemon's apply runs); that the DRIVER reaches and re-dispatches the review
   step with no operator is pinned by the existing #193 driver-layer test
   (`a_committed_review_step_that_declares_the_reviewer_leg_is_the_runs_own_dispatch`)
   and the generic bounded-retry rules
   (`a_diagnosed_frontier_retries_unless_reserved_by_the_operator`,
   `refusal.run.retry_bound` in `run_control`) — those are unchanged by this
   delta and were not re-witnessed end-to-end against a live daemon here.
2. **The live spine's ~27-minute reviewer still exceeds the bounded budget.**
   The bounds are unchanged, so a reviewer whose verdict lands later than the
   run's own retry budget allows (~4 attempts and their backoff) still parks
   the run typed (`effect.review_timeout`, `needs-attention`) — but no longer
   on a false "the prompt was not delivered", and no longer after deleting the
   leg's verdict. Convergence with zero operator dispatch holds for any
   reviewer whose verdict lands inside the recorded budget; the measured
   p6-132 verdict (05:27:56Z, ~28 min after the first prompt) is outside even
   the fixed shape's window — widening that window was explicitly fenced off.
3. **The headless substrate re-delivers on every attempt** (its prompt IS the
   reviewer's run): the resume rule applies to the pane substrate only. The
   effect-layer headless tests (`the_run_dispatches_its_own_reviewer…` and
   negatives) stay green through `just ci`.
4. The timeout outcome's structured facts ride its message, not `result`
   (the durable shape drops `result` for a non-succeeded effect); a caller
   that only reads the `result` of an ambiguous outcome sees `null` — that is
   the pre-existing `hf-outcome/v1` contract, unchanged.
5. No end-to-end live-daemon p1→p8 run was executed (off-limits per the
   brief); the two layers above are the evidence.
