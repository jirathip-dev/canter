## 1. The defect, re-measured on the live fleet (read-only)

Armed supervision was never retired for a finished run, so the driver owed every dead run a
classification pass on its own cadence. Re-read on this host at the moment this lane ran:

```console

    "select coalesce(i.status,'(no instance row)') s, count(*) from supervisions

    "select count(*), count(distinct instance_id), sum(desired='armed') from supervisions;"

```

75 of 82 armed rows belong to `done` / `invalidated` runs; the live fleet is five runs (three of
them the long-parked #224/#258/#261). Every one of those 75 rows was still on the due list, and
the recorded `last_check_reason` of a finished row was its PERMANENT re-classification
(`supervision.completed` for 23 `done` rows, `supervision.invalidated` for 50 `invalidated` ones).

## 2. What the fix does

A run the engine's own record has made terminal (`done` | `invalidated`) is retired — it stops
being armed, is never scheduled a pass again, and the retirement is recorded ON the row:

- `src/state.rs` — `retire_terminal_supervision_locked` is the ONE writer: `desired = 'disabled'`,
  `retired_state` (the terminal state that caused it), `retired_at` (the instant), and the run's
  pending wake slot is dropped with the arm it can no longer consume. It never creates a row, so a
  run that was never supervised stays exactly that.
- The writer is called from the transaction that ALREADY records the terminal transition:
  `release_run` (a release), `invalidate_grant` (a material issue edit) and
  `invalidate_grants_below_current` (an epoch rotation / restore) — each retires exactly the runs
  it invalidates, in its own step, with no operator action beyond the control itself.
- `commit_supervision_check` — the driver's own check that observes a terminal run retires it in
  the SAME transaction: this covers the run whose own delivery completes it (the `done` is written
  by that same transaction, issue #152) and a row a PRE-FIX fleet still carries armed for a
  terminal run (the boot pass reconciles every armed run exactly once, then never again). The
  retirement runs AFTER the queue advance on purpose: the advance arms the continuation from the
  delivering run's own authorization, read from the very row the retirement flips (measured while
  developing: retiring before the advance made the successor inherit `disabled` and stopped the
  queue — the witness `the_real_daemon_advances_the_queue_to_the_next_issue_without_another_request`
  is the regression fence for that).
- `src/supervision.rs` — `TERMINAL_RUN_STATES`/`terminal_run_state` (the engine's own terminal
  vocabulary), and the `supervision.status` block now carries `retired_state`/`retired_at`;
  `render_human` names the retirement. `desired` stays the closed set `armed` | `disabled`.
- Schema: `m0013_supervision_retirement_v13`, `SCHEMA_VERSION` 13 — two additive
  `supervisions` columns (`retired_state`, `retired_at`, both `''` when never retired), so a reader
  tells a retired-and-finished run from a never-supervised one (no row at all) and from an
  operator-disabled row (both empty).
- Docs updated with it: `docs/contracts/spec-state.md`, `docs/contracts/spec-daemon.md`, `README.md`,
  `docs/OPERATIONS.md`, `docs/RELEASING.md`, `skills/canter/SKILL.md`, `CHANGELOG.md`,
  `scripts/test-build-archive.py` (the release-provenance self-test pins schema v13 / chain m0013).

Live states are untouched: a `running` (including parked) run, `blocked`, `human_queue` and
`paused` keep being classified exactly as now, and a paused run keeps its row and stays ineligible.

## 5. Expectation changes in existing suites (disclosed, not hidden)

The issue changes the contract for terminal runs, so expectations that ENCODED the defect moved
with it — every change is annotated with `Issue #311` at the site:

- `tests/queue_advance.rs` (5 legs + the shared `reconcile` helper): a replay of the delivering run
  now reaches no check at all (`None`) instead of re-deriving the delivery; the durable claims are
  kept by reading the recorded delivery with a pure `verified_delivery` read (still recognized) and
  by the unchanged "consumed record is immutable / one cursor move" assertions. The two assertions
  that read the delivering run's last check as `completed`/`COMPLETED` now read the recorded
  retirement (`retired_state == "done"`, `retired_at` set) — a finished run is no longer
  re-classified on every tick.
- `tests/restart_pause_continuity.rs` (7 legs + the helper + the `wait_for_checks` wrapper that lost
  its last caller): the crash-matrix progress signature was "the resumed boot pass commits ONE more
  check of the delivering run". That run is retired by its own completion now, so the matrix reads
  the retirement (`wait_for_retirement`) and asserts the check count does NOT move — the crash
  matrix's real claims (one consumed delivery, one cursor row, one dispatched run, nothing
  replayed) are unchanged and still asserted.
- No production behaviour outside the terminal-run contract changed; the successor-arming path,
  the pause hold, the retry/refusal surfaces and the board are untouched.
