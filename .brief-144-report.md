## Root cause (reproduced live against herdr 0.9.0, then in-test at the base)

The failing row is the one the start path runs to RECORD the lane↔pane/agent binding:

```
herdr pane report-metadata <pane> --source custom:canter-lane --agent <lane> \
  --token canter_lane=<lane> --token canter_generation=<n>
```

Measured on this host with the reference herdr CLI, in the allowlisted adapter environment
(`env -i PATH=… HOME=…`, exactly what `run_typed` passes):

```
-- 3) herdr pane report-metadata (the row that recorded the binding):
exit=0
stdout bytes:        0 | stderr bytes:        0
```

It **succeeds with exit 0 and prints no document at all**. `herdr_call` (`src/adapters.rs:1625`,
parse at `src/adapters.rs:1633`) required a JSON document from every row, so the recording that
had already landed was refused `refusal.malformed.output` with the message *"the Herdr row
returned unparsable JSON"* — naming neither the row nor the payload. That is the whole defect:
pane created, agent started, binding recorded, step refused.

Measured confirmations in the same log (`.probe-live-herdr-measurement.log`):

* `herdr workspace create --cwd … --label … --no-focus` → **valid JSON**, exit 0
  (`result.root_pane.pane_id`, `result.workspace.workspace_id`).
* `herdr agent start <lane> --kind hermes --pane … -- <role args>` → **valid JSON**, exit 0
  (the started agent rides under `result.agent`, `type: agent_started`).
* the issue's own run: its pane/agent exist with `tokens {canter_generation, canter_lane}` — i.e.
  the `report-metadata` recording DID land; only its (empty) stdout was parsed.
* LATENT second defect in the same contract: `herdr agent get <lane>` returns
  `{"id":…,"result":{"agent":{…},"type":"agent_info"}}` — the row is nested one level deeper than
  the extractor assumed (`herdr_call` unwraps `result`, then `LaneBinding::read` read the ENVELOPE
  as the row). Even with the empty-stdout row fixed, that read-back would have refused
  `refusal.stale.generation` (`agent ""`), so it is part of the same result-contract fix.

In-test RED at the base source (new fixtures only): `the_role_starts_in_a_herdr_pane_created_in_
the_lane_worktree` refuses with the issue's exact message, raw exit **101**
(`.probe-p0-base-red.log`):

```
assertion `left == right` failed: Some("the Herdr row returned unparsable JSON")
  left: "refused"
 right: "succeeded"
```

## Item 4a — supervision must back off a run it can never progress — DONE-VERIFIED

Implemented (`src/daemon.rs:1360-1440`): the dispatch hook keeps a per-run ladder of consecutive
refused continuations. After a refusal the next ATTEMPT is allowed only after
`min(check_interval × 2^(streak-1), 900 s)` of the run's own policy interval, so the attempt rate
decays instead of tracking the tick; any dispatch that reaches the engine clears the ladder (an
operator repair still recovers the run), a refusal of a DIFFERENT step starts a fresh ladder, and a
paced-out attempt is named on the daemon log (`supervision.dispatch_backoff`) without recording a
new refusal or changing the run's classification. At the production 60 s interval this is ≈6 attempts
in the first hour instead of 60.

* `cargo test --locked --test supervision_dispatch_refusal a_repeatedly_refused_continuation_is_not_redispatched_every_tick`
  → raw exit **0** (`.probe-t6-backoff-green-measured.log`): over a window in which the driver
  committed **4 checks** the engine saw **2 refused attempts** (measured in-test, printed by the
  test during the evidence run).
* Mutation probe **P5** (`back_off_wait` always allows) → FAILS, raw exit **101**
  (`.probe-p5-backoff-ladder.log`): `4 checks produced 4 refused attempts` — the tick cadence is
  exactly the attempt cadence without the ladder, which is the measured #141/#144 loop.
* The refusal itself is unchanged: the same test asserts the run still reports
  `reason=supervision.dispatch_refused`, `detail=refusal.admission.proof_stale`, `eligible=false`,
  and that the refused step still has **0** attempts (nothing ran).
* `cargo test --locked --test supervision_dispatch_refusal` → raw exit **0**, `4 passed`
  (`.probe-t7-dispatch-refusal-suite.log`); `cargo test --locked --test supervision` → raw exit **0**,
  `21 passed` (`.probe-t8-supervision-suite.log`), including the #141 tests that assert exactly one
  refused-dispatch line in the retry scenario.

## Item 4b — `state.poisoned` names the failed write — DONE-VERIFIED

Implemented (`src/state.rs:1417/1588/7686/7709`): `poison_on` stores the FIRST write-class failure
(`<code>: <message>`, e.g. `state.write_full: … : SQLite disk full (SQLITE_FULL) …`) and
`ensure_writable` renders it: `state/audit writes previously failed: <cause>; mutations are refused
until the daemon restarts`. Fail-closed behaviour is unchanged (read-only queries keep working,
every later mutation still refuses `state.poisoned` until a restart).

* `cargo test --locked --test daemon_rpc readonly_state_dir_fails_closed_and_poisons_mutations`

## Limitations / NOT verified

1. **The prompt row (`p4`) was not measured.** The fix is scoped to the start path; the prompt path
   goes through the same `herdr_agent_get_row` read-back fix, but `herdr agent prompt <lane> <text>
   --wait --timeout <ms>`'s own printed document was NOT measured (the CLI help documents its
   failure modes, not its success payload). If it prints no document either, the next acceptance
   run will refuse at `p4` — and thanks to item 1 that refusal will name the exact row and the raw
   stdout instead of "unparsable JSON".
2. Item 3's live no-`pane_id` row was not reproducible (see item 3).
3. `agent start` on a pane that has just been created can answer `agent_pane_busy` (exit 1,
   `agent target pane … is not an available shell`) while the new shell reaches its prompt —
   observed once on this host while probing, and NOT part of this issue's scope. It surfaces as a
   classified `refusal.exit`/failed step with the CLI's own stderr, never as malformed output.
4. No live end-to-end acceptance run (issue #132 fixture, fresh grant, armed supervision) was
   performed by this lane: it mutates live host state (worktrees, grants, Herdr panes) that the
   orchestrator owns. The fix is witnessed at the row contract (live CLI measurements + fake
   executables pinned to those measurements) and at the daemon/dispatch level.
5. The `test` and `security` gate exits are in the final gate section above (both raw exit 0), and the
   fully gated code head is `482439e6be644ee175a8ebd5c72c6076fe5cdc12`.
