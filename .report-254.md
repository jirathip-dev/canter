## 1. The defect, reproduced from the row shapes the daemon writes

The live store of the reported acceptance run writes TWO fix-round dispatches
(`ik_…-p6-245-…`, `ik_…-p6-250-…`); both have `outcome.result = null` and the
whole returned document in the RESPONSE column:

    outcome:  {"error":null,"result":null,"status":"succeeded", … }
    response: {"ok":true,"result":{"feature_head":"e7bf162…","verdict":"fail",
               "fix_round":{"schema":"hf-fix-round/v1","round":1,"bound":3,
                            "feature_head":"e7bf162…","lane":"lane-fd0ec9…"} …}}

`newest_fix_round_locked` selected `request_line, outcome … outcome LIKE
'%fix_round%'` and required `outcome.result.fix_round.schema ==
"hf-fix-round/v1"`, so `evidence.fix_round` was `None` in production and the
classifier fell through to a bare `supervision.review_failed` — the reported
park. The state-level test that pinned the reader constructed exactly the shape
production never writes, so the suite stayed green while the live path was dead.

## 2. Policy implemented (the issue's required fix 1) and why

**Read the recorded handoff from where the daemon ACTUALLY persists it: the
apply row's RESPONSE document** (`hf-rpc-response/v1`, `result.fix_round`),
with the `outcome` column read beside it.

Rejected alternative: "persist the facts into the step's outcome at resolve
time". That would change the daemon's write path for a read-model defect, and
every other recorded read model in this repository already reads a dispatch's
own result from the response column (`run_dispatch_context`,
`delivery_certificate_locked` — both `COALESCE(response, '')`); reading the
response keeps ONE write path and follows the existing convention. The
reader's validation is unchanged: an `hf-fix-round/v1` document with all four
named fields (`round`, `bound`, `lane`, `feature_head`), or nothing.

## 3. The other three required fixes

- **Head match (required fix 2 / AC2).** The handoff is keyed to the head the
  newest recorded review evidence names (the real sequence: recorded at
  `e7bf162…`, the repair leg may advance the branch afterwards). A handoff
  naming ANOTHER head is no longer silent: it is its own typed fix-round
  disposition, `supervision.fix_round_head_moved` (class `needs-attention`),
  whose detail names the remedy FIRST — the fix leg's recorded lane — then
  both 12-character head prefixes. The recorded lane is the remedy either way.
- **Never `review_failed` with a visible fix round (required fix 3).** With
  `evidence.fix_round` present the class is the fix-round disposition in both
  cases: `supervision.fix_round_dispatched` (`waiting-workers`, detail = the
  fix leg's lane) when the handoff names the newest evidence's head, the new
  `supervision.fix_round_head_moved` (`needs-attention`, lane + heads)
  otherwise, and the existing refusal/exhaustion codes stay untouched. The
  human read renders the moved case as "fix round recorded for another head
  (lane <lane> (handoff recorded at …, newest evidence at …))".
- **The run's own bounded check re-evaluation is DRIVEN (AC3).** The declared
  contract — "when the run's own newest recorded review evidence carries a
  non-passing check the driver drives the run's OWN bounded, attributed and
  journaled check re-evaluation" — was gated on `verdict == "pass"` (the #243
  deadlock shape), so it never fired for the recorded FAIL. The driver's
  derivation (`supervision::reevaluation_intent`) now accepts the recorded FAIL
  as the same precondition, through the SAME control (`run.reevaluate`, the
  same producer lookup, the same per-`(run, step)` bound of 3 counted from the
  durable journal, the same reason and attribution). The
  pass-shape derivation (`unverified_delivery_refusal`) is untouched, so the
  read-time refusal block of the tail and the classification are unchanged.
- **Dispatch path untouched, no dependencies (required fix 4).** The apply
  engine, the effect, the plan validation and the fix-round dispatch are
  byte-unchanged; the diff is a read model, one classification arm, one detail
  renderer and the driver's existing intent derivation. No new dependency.

## 6. Disclosed gaps (NOT verified in this lane)

1. No live reviewer leg runs to a written verdict (a synthetic fixture owns no
   harness) and the pane substrate is exercised only indirectly — the same
   disclosure the #238/#243 witnesses carry. The fixture's round-2 `pass` is
   written by the production evidence writer; it stands in for the reviewer's
   own written verdict.
2. The witness's `pass` record is written after the fixture waits out the
   wall-clock second (two records inside one second share `created_at`, and the
   read path breaks that tie on the evidence id) — in production the
   recomputation is a reviewer leg, minutes later.
3. The re-evaluation re-runs the producer **at the run's recorded certified
   head** (the control's own documented semantics); it does not observe the
   repair leg's pushed head, because nothing in the run's ledger re-collects
   it. Linking a repair delivery back into a re-review of the MOVED head is
   #238's own disclosed gap ("a fresh review of the moved head is still a
   separate dispatch") and is not addressed here. What this lane guarantees is
   the remedy: the handoff is visible, the disposition names the lane, and the
   bounded re-evaluation is driven instead of the run parking.
4. Driving the re-evaluation immediately after the handoff (before the repair
   lands) recomputes the recorded head and can come back failing — bounded by
   the control's own per-`(run, step)` bound (3, counted from the durable
   journal), which then parks typed. That is the control's documented
   behaviour, not a new gate.
5. The lane's branch is committed locally and NOT pushed (the dispatch carried
   no push instruction); nothing was merged and no PR was opened.
