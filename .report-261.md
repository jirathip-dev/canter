## The defect (as the issue measured it on the live host)

`redrive_queue_submission` (`src/state.rs`) walked a submission's parked (`waiting`) items and
called `admit_queue_item_in_tx`. The submit path arms supervision in the SAME transaction as
the runs it names (`arm_supervision_in_tx`, `src/state.rs`), but the re-drive path never did:
the run it admitted carried **no supervision row at all**, nothing could drive it, and it held
one of the per-repository counted slots (`counted_lane_footprints`, instance statuses
`new`/`running`/`human_queue`/`blocked`) forever. Releasing the inert runs by hand was the only
remedy, because no operator surface could arm a run afterwards.

## The policy implemented (issue #261 "Required fix" 1), and why

**Arm what you admit — with the authorization the submission itself committed; refuse the whole
control typed when the submission has none.**

- The arming source, in order, is ONE fact: (1) the authorization block
  (`params.supervision`) of the submission's own committed `queue.submit` request — the row
  the operator presented `--supervise arm` on, and the same row a later admission already reads
  its dispatch context from; (2) failing that, the supervision row of an already-admitted run of
  the same submission — the SAME authorization the submit path armed that run with (the same
  substitution the #96 advance makes from the delivering run's row). No policy value, interval
  or deadline is ever invented by the caller.
- The admitted run is armed with the SAME bindings the submit path uses: the submission's
  approved digest (`authorization_digest`), its boundary phase (`approved_boundary`) and its
  state epoch (`run_generation`).
- A submission that committed **no `armed` authorization** (supervision disabled: the documented
  default) refuses the WHOLE re-drive typed — `refusal.queue.supervision_unarmed` — BEFORE any
  item is admitted, naming the missing authorization and the remedy (re-submit the parked items
  with `--supervise arm`). **The control never admits an inert run**: admitting one would convert
  the transient cap hold it exists to repair into a permanent one, which is exactly the defect.

**The bounded, audited operator control (requirement 2):** `supervision arm --run RUN_ID`
(new RPC method `supervision.arm`, document `hf-supervision-arm/v1`). It arms EXACTLY ONE
already-admitted run that carries no arming authorization, re-applying the authorization the
run's OWN committed submission presented (same digest/boundary/epoch binding), and commits the
arm together with its hash-chained `supervision.arm` audit row in ONE transaction (one
idempotency key = one effect). Typed refusals: `refusal.supervision.terminal_run` (a terminal
run), `refusal.supervision.already_armed` (a run whose row is `armed` — it is already driven),
`refusal.supervision.unbound` (no committed submission admitted the run), and
`refusal.supervision.unarmed` (the submission committed no `armed` authorization — arming would
invent one the operator never gave).

**Surfaced (requirement 3 / AC4):** `supervision.status` of an ADMITTED run that carries no
supervision row answers `hf-supervision/v1` with `supervision.state: "unarmed"`,
`evaluation.reason: "supervision.unarmed_inert"`, `eligible:false`, the detail ("nothing will
drive this run's next step and it holds its counted slot until it is armed or released") and the
remedy (`supervision arm --run …`) — so "admitted, unarmed" is distinguishable from "armed,
waiting" BEFORE the slot blocks a re-admission. An unknown run and a run no submission admitted
keep `state.not_found`.

No behavior change to the dispatch path; no new dependencies; no gate weakened.
