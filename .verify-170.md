## 2. Changes made (bounded to #170's own Done-when)

- **N3 (implemented)** — `src/mutation.rs`: the collection wait's cadence is now
  BOUNDED. `COLLECT_POLL_INTERVAL_MS` (100 ms, the prompt path's own cadence)
  doubles towards `COLLECT_POLL_MAX_INTERVAL_MS` (5 s ceiling) inside
  `poll_pane_worker`; the step deadline is unchanged (the loop still returns
  `effect.worker_timeout` exactly at the deadline). With the default 1800 s
  collection deadline the wait costs 365 reads (~730 Herdr rows) instead of
  18,000 reads (~36,000 rows) at the fixed cadence. The six existing poll tests
  pass `initial == max` (constant cadence: they pin the loop mechanics, not the
  backoff).
- **N4 (invariant restated precisely, the issue's own second option)** —
  `src/daemon.rs` shutdown block: the invariant now names exactly what is joined
  and what is not. The supervision driver IS cancelled and joined before the
  lease is dropped, so no NEW reconciliation can journal into a closing daemon;
  the pane-collection worker (`canter-collect`) is DELIBERATELY detached because
  it must outlive the reconciliation that spawned it, bounded by the collection
  step's own deadline (1800 s default, 3600 s ceiling) — a join there would hold
  the daemon's shutdown for that whole window. It takes no lease
  (`put_daemon_lease` / `drop_daemon_lease` are the daemon's own
  startup/shutdown path only — `n4c.log`, raw exit 0: `359`/`427`) and writes
  only transactionally under the state lock, so a process exit mid-collection
  leaves its claim in flight for the boot reconciliation (the modelled
  ambiguous-claim path), never a half-written journal. The same restatement is
  recorded in `docs/contracts/spec-daemon.md` (pane-collection bullet). Joining
  was rejected on evidence: the thread's lifetime bound is the collection
  deadline (`n4d.log`, raw exit 0 — `prompt`/`collect_outcome` =
  `PROMPT_DEADLINE_DEFAULT_SECS` 1800 s at `mutation.rs:111`; ceiling
  `EFFECT_DEADLINE_CEILING_SECS` 3600 s at `53`).
- **N5 (implemented)** — `src/daemon.rs`: the in-memory duplicate-dispatch
  reservation is keyed by the exact `(run, step)` pair
  (`BTreeSet<(String, String)>`; `reserve_collection` / `release_collection`).
  A second dispatch of the SAME step is still answered `awaiting <step>`, but
  another step of the same run (or another run's same-named step) is never
  fenced by it. Process-local by design, as before; the durable claim journaled
  by the spawned dispatch is what survives a restart.
- **N1 (recorded as an accepted limitation)** — `docs/contracts/spec-daemon.md`
  new bullet "Continuation window scope (issue #170 N1, accepted limitation)":
  the durable window is keyed on the check's recorded ELIGIBILITY — any
  committed eligible check opens or holds it (an in-flight collection wait, an
  ordinary dispatchable frontier, and the progress-timeout case) — so
  `continuation.reports` counts eligible-check episodes (one per window, never
  one per check) and the TUI's "continuation window: OPEN (N reports)" line
  renders that same counter: a window/report dedup counter, not a stall counter.
  No safety impact (`dispatch_intent` still gates on `evidence.in_flight`). The
  misleading comments at `src/state.rs:11682-11687` and `13531` now say
  "eligible window" and point at the contract. A code fix was NOT taken: the
  reported `eligible` field is the durable window state (the status surface
  renders `row.continuation_open` once a check is committed), so re-keying the
  window would either falsify the recorded eligibility report (issue #152's
  contract: a frontier reported eligible is exactly a dispatchable one) or need
  a new durable column and surface — wider than #170.
- **N2 (recorded as an accepted limitation)** — `docs/contracts/spec-daemon.md`
  (lane-base bullet) and `docs/contracts/spec-plans.md`: an unprovable published
  base (absent or unreadable `origin` ref) on `checkout`/`worktree_create` fails
  with the same typed `effect.merge.failed` the merge step's published-base
  proof uses; the shared fail-closed proof keeps its merge-flavoured name on
  this route, and the message names the lane-base read.
- **N6 (recorded as an accepted limitation)** — `docs/contracts/spec-daemon.md`
  (pane-collection bullet) and `docs/contracts/spec-plans.md`: a pane-substrate
  `collect_outcome` whose run never recorded a succeeded `harness_start` refuses
  `refusal.identity.incomplete` instead of evaluating the delta — the run's
  session identity is never invented, so there is no lane binding to verify the
  pane against; the fail-closed direction is deliberate.
